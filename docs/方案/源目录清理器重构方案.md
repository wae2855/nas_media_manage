# 源目录清理器重构方案

> 状态：✅ 已实施
> 日期：2026-05-29
> 涉及模块：storage、core/safety、monitor、api、webui、core/db

## 一、背景与问题

当前 `SourceCleaner` 实现存在以下问题：

1. **后缀名体系分裂**：`source_cleaner.py` 硬编码了 `VIDEO_EXTENSIONS`/`SUBTITLE_EXTENSIONS`，与全局 `video_extensions`/`subtitle_extensions` 配置重复且可能不一致
2. **AI 分类是空壳**：`_ai_classify()` 永远返回 `("", "")`，勾选 AI 无任何效果
3. **AI 定位错误**：当前 AI 定位为"规则处理不了的交给 AI"，但用户需求是 AI 对整体做分析检核，而非仅处理规则盲区
4. **清理模式语义不清**：`keep_media_only` 和 `keep_media_related` 两种模式下 `protect_extensions`/`delete_extensions` 的作用没有明确区分
5. **文件夹处理不完整**：黑名单目录（如 `Sample/`）没有整目录处理逻辑；空目录直接 `rmdir` 不入回收站
6. **前端高级配置不可用**：`toggleInfoPanel` 控制的面板在清理器未启用时被 `collapsed-section` 隐藏，点击无反应
7. **合并策略未定义**：规则和 AI 结果如何合并没有设计

## 二、设计目标

1. 后缀名体系统一，清理器与扫描器共享同一套媒体文件定义
2. AI 作为独立分析层，对源目录整体分析，与规则结果合并
3. 用户可选择合并策略（并集/交集），并知晓误删可恢复
4. 文件夹和文件分别有明确的处理规则
5. 前端交互完整可用，配置项语义清晰

## 三、后缀名体系统一

### 3.1 现状

| 来源 | 定义方式 | 用途 |
|------|---------|------|
| `FileScanner.VIDEO_EXTENSIONS` | 类常量 | 扫描器识别视频文件 |
| `FileScanner.SUBTITLE_EXTENSIONS` | 类常量 | 扫描器识别字幕文件 |
| `config.video_extensions` | 用户配置 | 覆盖扫描器默认值 |
| `config.subtitle_extensions` | 用户配置 | 覆盖扫描器默认值 |
| `SourceCleaner.VIDEO_EXTENSIONS` | 硬编码常量 | 清理器判断媒体文件 |
| `SourceCleaner.SUBTITLE_EXTENSIONS` | 硬编码常量 | 清理器判断字幕文件 |
| `source_cleaner.delete_extensions` | 用户配置 | 清理器指定删除后缀 |
| `source_cleaner.protect_extensions` | 用户配置 | 清理器指定保护后缀 |

### 3.2 重构方案

**删除 `SourceCleaner` 中的硬编码常量，改为从全局配置读取。**

```
媒体文件定义（全局共享）：
  video_extensions + subtitle_extensions → 定义"什么是媒体文件"
  扫描器和清理器共用此定义

清理器附加配置：
  delete_extensions → 在媒体文件定义之外，额外指定要删除的后缀
  protect_extensions → 在媒体文件定义之上，额外指定要保护的后缀
```

**优先级**：`protect_extensions` > 全局媒体后缀 > `delete_extensions` > 模式默认行为

### 3.3 具体改动

`SourceCleaner.__init__` 中：
```python
# 删除硬编码常量
# VIDEO_EXTENSIONS = {...}
# SUBTITLE_EXTENSIONS = {...}

# 改为从全局配置读取
self.video_extensions = set(
    ext.lower() for ext in config.get("video_extensions", [])
) or {".mkv", ".mp4", ".avi", ".ts", ".mov", ".wmv", ".m2ts", ".flv", ".webm", ".m4v"}

self.subtitle_extensions = set(
    ext.lower() for ext in config.get("subtitle_extensions", [])
) or {".srt", ".ass", ".ssa", ".sub", ".idx", ".smi", ".vtt", ".sup"}

self.media_extensions = self.video_extensions | self.subtitle_extensions
```

### 3.4 前端配置调整

基础配置中已有 `video_extensions`/`subtitle_extensions`（高级配置区域），清理器不再重复定义。清理器高级配置中的 `delete_extensions` 和 `protect_extensions` 保留，但 hint 文案需更新：

- `delete_extensions`："指定额外删除的后缀名（逗号分隔），媒体文件（视频+字幕）由全局配置定义，此处指定非媒体文件中需要删除的，如 .url,.log"
- `protect_extensions`："指定额外保护的后缀名（逗号分隔），优先级最高，即使模式要求删除也会被保留，如 .nfo,.jpg"

## 四、清理模式语义重定义

### 4.1 两种模式

| 模式 | 保留 | 删除 | delete_extensions 作用 | protect_extensions 作用 |
|------|------|------|----------------------|----------------------|
| `media_only` | 视频+字幕 + protect列表 | 其余全部 | 无意义（已默认全删非媒体） | 从删除列表中豁免 |
| `media_and_related` | 视频+字幕 + 同名关联文件 + protect列表 | 仅 delete列表 + 黑名单匹配 + 垃圾视频 | 明确指定要删什么 | 额外保护 |

### 4.2 同名关联文件定义

`media_and_related` 模式下，与某视频文件同目录且同基名（或基名前缀匹配）的非媒体文件视为"关联文件"，予以保留。

匹配规则：
- 完全同基名：`电影.mkv` → `电影.nfo`、`电影.jpg`
- 基名+后缀：`电影.mkv` → `电影-fanart.jpg`、`电影-poster.png`
- 基名+语言标记：`电影.mkv` → `电影.zh.srt`（字幕已在媒体定义中）

实现：提取视频文件基名（去掉扩展名），同目录下其他文件基名以此开头的视为关联。

### 4.3 垃圾视频检测

两种模式下均生效：
- 视频文件大小 < `junk_video_max_size_mb` → 标记为垃圾视频
- 默认值 50MB（典型广告/预告片大小）
- 设为 0 关闭此检测

## 五、AI 分析层设计

### 5.1 AI 定位

AI 不是规则的补充，而是对整体的独立分析层。AI 从全局视角分析源目录中的文件，能够识别规则无法覆盖的模式：

- **容量异常**：同一目录下 5 个视频，1 个 20GB 其余 200MB，小的大概率是广告
- **命名混淆**：广告视频故意使用与正片相似的文件名
- **目录级判断**：整个 `Sample/` 或 `预告/` 目录下的文件都是垃圾
- **关联识别**：`.nfo` 和海报图片与视频的关联关系

### 5.2 AI 分析流程

```
扫描源目录全部文件
        │
        ├── 规则引擎分析 → rule_results: {path: "keep"|"delete", reason}
        │
        └── AI 整体分析 → ai_results: {path: "keep"|"delete", reason}
                │
                ▼
        合并策略（用户选择）
                │
        ┌───────┴───────┐
        │               │
      并集模式        交集模式
   任一判删则删    两者都判删才删
        │               │
        ▼               ▼
     最终清理列表     最终清理列表
```

### 5.3 合并策略

| 策略 | 规则=keep, AI=delete | 规则=delete, AI=keep | 规则=keep, AI=keep | 规则=delete, AI=delete |
|------|---------------------|---------------------|-------------------|----------------------|
| **并集**（激进） | 删 | 删 | 保留 | 删 |
| **交集**（保守） | 保留 | 保留 | 保留 | 删 |

- 默认推荐 **交集**（保守），减少误删
- 前端需明确提示："误删文件可从回收站恢复"
- 新增配置项 `merge_strategy`：`union`（并集）/ `intersection`（交集，默认）

### 5.4 AI 分析实现

AI 分析以**目录**为单位进行，而非逐文件。每次分析一个目录下的所有文件，AI 可以看到完整上下文。

**输入构造**：
```python
{
    "directory": "/vol1/downloads/Movie.2024/",
    "files": [
        {"name": "Movie.2024.1080p.mkv", "size_mb": 20480, "ext": ".mkv"},
        {"name": "Sample.mkv", "size_mb": 150, "ext": ".mkv"},
        {"name": "Movie.nfo", "size_mb": 0.01, "ext": ".nfo"},
        {"name": "poster.jpg", "size_mb": 0.5, "ext": ".jpg"},
        {"name": "广告视频.mkv", "size_mb": 200, "ext": ".mkv"},
        {"name": "readme.txt", "size_mb": 0.01, "ext": ".txt"},
    ]
}
```

**输出要求**：
```json
{
    "analysis": "该目录包含一部电影(Movie.2024.1080p.mkv, 20GB)，其余视频文件较小，Sample.mkv和广告视频.mkv为广告/样本，应删除。NFO和海报为电影关联文件，应保留。readme.txt为无关文件。",
    "decisions": {
        "Sample.mkv": {"action": "delete", "reason": "样本视频，150MB远小于正片20GB"},
        "广告视频.mkv": {"action": "delete", "reason": "广告视频，200MB远小于正片20GB"},
        "Movie.nfo": {"action": "keep", "reason": "电影元数据文件"},
        "poster.jpg": {"action": "keep", "reason": "电影海报"},
        "readme.txt": {"action": "delete", "reason": "无关文本文件"}
    }
}
```

### 5.5 AI 提示词设计

```
你是 影音库AI智能整理的源目录清理助手。你的任务是分析源目录中的文件，判断哪些是垃圾文件应该删除，哪些是影视相关文件应该保留。

【分析原则】
1. 整体视角：分析整个目录的文件构成，而非孤立判断单个文件
2. 容量对比：同一目录下，视频文件大小差异显著时，小文件大概率是广告/样本/预告
3. 命名模式：文件名含 sample、trailer、预告、花絮、广告等关键词的应删除
4. 关联识别：与视频同名的 .nfo、.jpg、.png 等是影视元数据/海报，应保留
5. 字幕文件：.srt、.ass 等字幕文件应保留
6. 保守原则：无法确定时倾向于保留，避免误删

【判断标准】
- 主视频文件（通常最大的视频文件）→ 保留
- 字幕文件 → 保留
- 与主视频同名的元数据/海报 → 保留
- 样本/预告/广告视频（明显小于主视频）→ 删除
- BT下载附带的无用文件（.url, .txt说明, 下载站广告图）→ 删除
- 无法判断的文件 → 保留

【输出格式】
请严格按以下JSON格式返回，不要添加任何解释文字：
{
    "analysis": "简要分析说明",
    "decisions": {
        "文件名": {"action": "keep或delete", "reason": "判断理由"}
    }
}
```

### 5.6 AI 调用集成

复用现有 `LLMScraper` 的 LLM 调用基础设施（`urllib.request` + OpenAI API），不引入新依赖：

```python
def _ai_analyze_directory(self, dir_path: str, files: list) -> dict:
    llm_config = self.config.get("llm", {})
    if not llm_config.get("api_key"):
        return {}

    prompt = self._build_cleaner_prompt(dir_path, files)
    response = self._call_llm(llm_config, prompt)
    return self._parse_ai_response(response)
```

使用 `fast_model`（如果配置了）以降低成本和延迟，因为清理判断比元数据刮削简单。

## 六、权限检测

### 6.1 现有权限检测机制

系统已有 `permission_checker.py` 提供统一的路径权限检测：

- `check_path_permission(path, need_write)` — 检测单条路径的读写权限
- `check_config_permissions(config)` — 批量检测配置中所有路径的权限
- `is_app_managed_path(path)` — fnOS 应用管理路径免检
- 前端 `testPathPermission(inputId, needWrite)` — 输入框失焦自动检测
- 保存配置时 `saveSection('basic')` 会先调用 `/config/check-permission` 批量检测

当前已检测的路径：`source_dir`（只读）、`temp_dir`（读写）、`log_dir`（读写）、`recycle_dir`（读写）、入库规则根目录（读写）。

### 6.2 清理器需新增的权限检测

| 路径 | 权限要求 | 检测时机 |
|------|---------|---------|
| `source_dir`（清理器操作） | 读写 | 清理器启用时，源目录需写权限才能移入回收站 |
| `recycle_dir` | 读写 | 已有检测，但需确保清理器启用时也校验 |

**具体改动**：

1. **`check_config_permissions()`** 新增：当 `source_cleaner.enabled=true` 时，`source_dir` 的权限要求从只读升级为读写（因为清理器需要将文件移入回收站，涉及源目录的写操作）

2. **前端 `saveSection('basic')`**：保存基础配置时，如果清理器已启用，`source_dir` 的权限检测需传 `need_write=True`

3. **清理器执行前检测**：`source_cleaner_execute` API 在执行前调用 `check_path_permission(recycle_dir, need_write=True)` 确保回收站可写

4. **前端清理器配置保存**：新增清理器配置保存时的权限检测逻辑，确保 `source_dir` 和 `recycle_dir` 都有写权限

### 6.3 实现方式

```python
# permission_checker.py - check_config_permissions() 新增逻辑
source_cleaner = config.get("source_cleaner", {})
if source_cleaner.get("enabled"):
    # 清理器启用时，source_dir 需要写权限
    if source_dir and not is_app_managed_path(source_dir):
        r = check_path_permission(source_dir, need_write=True)
        _add_issue("source_dir (清理器需写权限)", source_dir, r)
```

## 七、回收站结构设计

### 7.1 现有回收站结构

```
{recycle_dir}/
└── {YYYY-MM-DD}/           # 按日期分组
    └── [源目录]/            # 来源分区（_recycle_subpath 生成）
        └── {相对路径}/
            ├── {文件名}
            └── {文件名}.meta
    └── [入库目录]/
        └── ...
    └── [其他]/
        └── ...
```

`.meta` 文件内容：
```json
{
    "original_path": "/vol1/.../电影.mkv",
    "source_zone": "source",
    "reason": "source_cleanup",
    "task_id": "T20260529-001",
    "moved_at": "2026-05-29T10:30:00",
    "file_size_mb": 20.5
}
```

### 7.2 现有问题

1. **`move_to_recycle` 拒绝目录**：当前 `if os.path.isdir(real): return False`，无法将空目录移入回收站
2. **来源分区不完整**：只有 `[源目录]`、`[入库目录]`、`[其他]` 三个分区，清理器产生的文件没有独立分区
3. **reason 字段不统一**：各调用方使用不同的 reason 值，没有枚举约束

### 7.3 重构方案

#### 7.3.1 支持目录移入回收站

新增 `move_dir_to_recycle()` 函数，用于将整个目录移入回收站（空目录、黑名单目录）：

```python
def move_dir_to_recycle(dir_path: str, recycle_dir: str,
                         reason: str = "", source_dir: str = "",
                         import_roots: list = None,
                         extra_meta: dict = None) -> tuple:
    """将目录移入回收站，保留目录结构"""
```

实现逻辑：
1. 验证路径安全性
2. 构造回收站目标路径（与文件相同的日期+分区结构）
3. `os.rename()` 整个目录（失败时 `shutil.copytree` + `shutil.rmtree`）
4. 在目录旁创建 `.dir.meta` 文件记录元信息

#### 7.3.2 来源分区扩展

```
{recycle_dir}/
└── {YYYY-MM-DD}/
    ├── [源目录]/            # 来自源目录的文件（任务流清理、忽略操作）
    ├── [入库目录]/          # 来自入库目录的文件（去重替换、任务删除）
    ├── [清理器-源目录]/     # 清理器从源目录清理的文件
    └── [其他]/              # 无法归类的文件
```

新增 `[清理器-源目录]` 分区，与任务流产生的回收文件区分。清理器调用 `move_to_recycle` 时传入 `reason` 前缀 `source_cleaner:`，`_recycle_subpath` 根据 reason 区分分区。

#### 7.3.3 reason 字段标准化

| reason 值 | 来源 | 说明 |
|-----------|------|------|
| `source_cleanup` | 任务流 | 任务完成后源文件清理 |
| `task_delete` | API | 用户删除任务 |
| `dedup_replace` | 任务流 | 去重替换旧文件 |
| `quality_replace` | 任务流 | 质量替换旧文件 |
| `import_overwrite` | 入库 | 入库目录同名覆盖 |
| `source_cleaner:non_media` | 清理器 | 非媒体文件 |
| `source_cleaner:delete_extension` | 清理器 | 匹配删除后缀 |
| `source_cleaner:junk_video` | 清理器 | 垃圾视频 |
| `source_cleaner:blacklist_pattern` | 清理器 | 黑名单匹配 |
| `source_cleaner:ai_delete` | 清理器 | AI 判定删除 |
| `source_cleaner:empty_dir` | 清理器 | 空目录 |
| `source_cleaner:blacklist_dir` | 清理器 | 黑名单目录 |

#### 7.3.4 回收站完整结构

```
{recycle_dir}/
└── 2026-05-29/
    ├── [源目录]/
    │   └── 电影/
    │       ├── 电影.2024.1080p.mkv
    │       ├── 电影.2024.1080p.mkv.meta
    │       ├── 电影.2024.1080p.zh.srt
    │       └── 电影.2024.1080p.zh.srt.meta
    ├── [入库目录]/
    │   └── 电影/
    │       ├── 旧版电影.mkv
    │       └── 旧版电影.mkv.meta
    ├── [清理器-源目录]/
    │   └── 电影/
    │       ├── Sample.mkv
    │       ├── Sample.mkv.meta
    │       ├── RARBG.txt
    │       ├── RARBG.txt.meta
    │       ├── Sample/              # 黑名单目录整体移入
    │       ├── Sample.dir.meta
    │       ├── 空目录/               # 空目录移入
    │       └── 空目录.dir.meta
    └── [其他]/
        └── unknown_file.txt
            └── unknown_file.txt.meta
```

#### 7.3.5 过期清理兼容

`recycle_cleanup()` 函数需兼容目录：
- 扫描 `.meta` 和 `.dir.meta` 文件
- `.dir.meta` 过期时，`shutil.rmtree()` 删除整个目录
- `.meta` 过期时，继续删除单个文件（现有逻辑）

### 7.4 回收站浏览与恢复

#### 7.4.1 问题

当前回收站只有"移入"能力，没有"恢复"能力。用户无法：
- 查看回收站中有哪些文件
- 知道文件是从哪里删除的
- 一键恢复文件到原位置

`.meta` 文件记录了 `original_path`，但只能通过手动查看文件才能获取。

#### 7.4.2 回收站浏览 API

**`GET /api/recycle/list`**

查询参数：`zone`（分区过滤）、`reason`（原因过滤）、`limit`、`offset`

响应：
```json
{
    "code": 200,
    "data": {
        "items": [
            {
                "recycle_path": "/data/recycle/2026-05-29/[清理器-源目录]/电影/Sample.mkv",
                "original_path": "/vol1/downloads/电影/Sample.mkv",
                "source_zone": "source",
                "reason": "source_cleaner:junk_video",
                "moved_at": "2026-05-29T10:30:00",
                "file_size_mb": 150.2,
                "task_id": "",
                "is_dir": false,
                "restorable": true
            }
        ],
        "total": 25,
        "zones": {
            "[源目录]": 10,

            "[清理器-源目录]": 8,

}
```

`restorable` 字段：检查 `original_path` 的父目录是否仍然存在且可写，如果原位置已被其他文件占据也标记为不可直接恢复。

#### 7.4.3 回收站恢复 API

**`POST /api/recycle/restore`**

请求体：
```json
{
    "items": [
        {"recycle_path": "/data/recycle/2026-05-29/[清理器-源目录]/电影/Sample.mkv"}
    ]
}
```

响应：
```json
{
    "code": 200,
    "data": {
        "restored": [
            {
                "recycle_path": "/data/recycle/2026-05-29/[清理器-源目录]/电影/Sample.mkv",
                "restored_to": "/vol1/downloads/电影/Sample.mkv",
                "status": "ok"
            }
        ],
        "failed": [
            {
                "recycle_path": "/data/recycle/2026-05-29/[源目录]/旧文件.mkv",
                "status": "conflict",
                "message": "原位置已存在同名文件"
            }
        ]
    }
}
```

恢复逻辑：
1. 读取 `.meta` 获取 `original_path`
2. 检查原位置父目录存在且可写
3. 检查原位置无同名文件（有则标记冲突）
4. `os.rename()` 移回原位置（失败时 `shutil.copy2` + `os.remove`）
5. 删除对应的 `.meta` 文件
6. 目录恢复：读取 `.dir.meta`，`os.rename()` 整个目录回原位置

冲突处理选项（前端可让用户选择）：
- 跳过（默认）
- 覆盖（先移走冲突文件到回收站）
- 重命名（恢复文件加后缀 `_restored`）

#### 7.4.4 回收站永久删除 API

**`POST /api/recycle/delete`**

请求体：
```json
{
    "items": ["/data/recycle/2026-05-29/[清理器-源目录]/电影/Sample.mkv"]
}
```

逻辑：`os.remove()` 文件 + 删除 `.meta`；目录则 `shutil.rmtree()` + 删除 `.dir.meta`。

## 八、文件夹处理规则

### 8.1 处理流程

```
扫描源目录
    │
    ├── 文件级处理
    │   ├── 规则分类 → keep/delete
    │   └── AI 分类 → keep/delete
    │
    ├── 目录级处理
    │   ├── 黑名单目录匹配 → 整目录标记删除
    │   └── 非黑名单目录 → 仅处理其中文件
    │
    └── 后处理
        ├── 文件清理后检测空目录
        └── 空目录移入回收站（保留恢复可能）
```

### 6.2 黑名单目录

当前 `blacklist_patterns` 支持文件名和路径匹配。新增**目录级黑名单**概念：

- 路径模式匹配 `*/Sample/*`、`*/sample/*` → 整个 `Sample/` 目录下所有文件标记删除
- 目录名匹配 `预告`、`花絮` → 整个目录标记删除
- 目录级黑名单命中时，目录内所有文件（包括视频）都标记删除

实现：在 `preview()` 中先扫描目录结构，匹配黑名单的目录整体加入清理列表。

### 8.3 空目录处理

清理文件后，自底向上检测空目录：

- 当前逻辑：`os.rmdir()` 直接删除 → **改为 `move_to_recycle()`**，保留恢复可能
- 仅清理源目录下的空目录，不清理源目录本身
- 空目录的 `.meta` 文件记录 `reason: "empty_dir_after_cleanup"`
