# 文档体系重构方案

> 目标：把当前分散、重复、边界不清的文档体系，整理为“AI 可导航、代码可关联、变更可闭环、长期可维护”的项目知识系统。

## 一、问题陈述

当前 `docs/` 已经积累了架构、方案、规范、计划、测试等内容，但存在几个问题：

1. **入口不够清晰**：AI 或新维护者不知道先读哪篇、再读哪篇。
2. **文档和代码关联弱**：文档按主题存在，但没有稳定表达“这个代码模块对应哪些文档，改代码时要同步哪些文档”。
3. **规范分散**：AGENTS.md、接口规范、开发流程规范、架构文档中都有规则，但职责边界不清。
4. **历史方案和当前事实混在一起**：已实施方案、待评审方案、架构现状文档容易互相覆盖。
5. **缺少决策日志**：关键架构选择有散落描述，但没有统一 ADR/决策记录入口。
6. **缺少维护制度**：没有定期检查文档漂移、失效链接、过期方案的机制。

## 二、目标

### 2.1 AI 高效导航

AI 应能通过 2-3 次跳转找到：

- 功能属于哪个模块；
- 入口代码在哪里；
- 相关 API、配置、测试、文档在哪里；
- 修改后要同步哪些文档；
- 需要跑哪些测试。

### 2.2 文档与代码强关联

每个主要代码层级都有对应文档：

- 项目入口文档：解释全局结构和导航。
- 架构文档：解释模块边界、数据流、依赖关系。
- 模块文档：解释具体模块职责、入口文件、扩展点、测试。
- 规范文档：约束代码、文档、测试、流程。
- 工作流文档：约束从想法到上线的闭环过程。
- 决策日志：记录为什么这样设计。

### 2.3 规范可执行

规范必须能指导 AI 执行，而不只是抽象原则。例如：

- Python 单文件建议不超过 500 行；
- API handler 不承载复杂业务逻辑；
- 新增配置项必须同步 loader/migration/validator/API/frontend/docs；
- 新增状态必须同步 lifecycle/API/frontend/tests/docs；
- 删除/覆盖影视文件必须走回收站安全路径。

### 2.4 历史内容可保留

原文档先备份，不在第一阶段删除。等新体系稳定后，再决定：

- 迁移为正式文档；
- 归档为历史资料；
- 删除出项目。

### 2.5 框架先行，事实后补

考虑到后续还会继续进行大面积代码架构重构，本次文档重构不应把当前实现细节写成“最终事实百科”。执行策略调整为：

- **先建立文档操作系统**：入口、索引、导航、规范、工作流、决策日志、归档机制。
- **轻量描述当前模块**：只写职责、入口文件、扩展点、测试入口，不深写马上会变化的内部实现。
- **代码重构后补全架构事实**：`architecture/` 和 `modules/` 的细节在 TaskContext、TaskLifecycle、pipeline services 等重构稳定后再补全。
- **避免重复返工**：当前阶段不重写所有旧架构文档，不删除旧文档，不把过期细节搬进新事实文档。

### 命名策略

建议新体系统一使用英文目录和文件名，原因：

- 对 AI 和工具链更稳定；
- 便于链接、搜索、跨平台处理；
- 中文标题保留在文档正文中。

旧中文文档先备份到 `_archive/`，重构后再决定是否保留中文路径。

## 四、文档类型职责

| 类型 | 职责 | 不应包含 |
|------|------|----------|
| `docs/README.md` | 文档入口，告诉读者先读什么 | 详细架构细节 |
| `docs/INDEX.md` | 项目索引，代码-文档-测试映射 | 长篇解释 |
| `docs/ai-map.md` | AI 修改任务导航 | 历史方案 |
| `product/` | 产品目标、用户工作流、术语 | 代码实现细节 |
| `architecture/` | 当前事实架构 | 过期方案、未实施设想 |
| `modules/` | 代码模块职责和扩展点 | 全局流程重复描述 |
| `standards/` | 必须遵守的规范 | 临时计划 |
| `workflows/` | 开发闭环流程 | 某个具体功能方案 |
| `decisions/` | ADR，记录为什么 | 任务清单 |
| `plans/` | 已批准计划和执行清单 | 当前架构事实 |
| `proposals/` | 待评审方案 | 已实施后的事实文档 |
| `testing/` | 测试策略、矩阵、已知失败 | 实现方案 |
| `_archive/` | 历史备份 | 当前事实引用 |

### 5.2 变更影响规则

每次代码变更必须判断是否需要同步文档：

| 改动类型 | 必须同步 |
|----------|----------|
| 新增 API | `architecture/api.md`, `standards/api.md` 如有规则变化, `docs/INDEX.md` |
| 修改状态 | `architecture/task-lifecycle.md`, `modules/pipeline.md`, 测试矩阵 |
| 新增配置项 | `architecture/configuration.md`, `standards/configuration.md`, `docs/INDEX.md` |
| 新增 Provider | `architecture/scraping.md`, `modules/scraper-providers.md` |
| 修改文件操作/删除逻辑 | `standards/safety.md`, `architecture/storage-filesystem.md`, 回归测试矩阵 |
| 新增业务模块 | `architecture/module-map.md`, `modules/<module>.md`, `docs/INDEX.md`, `AGENTS.md` 如影响 AI 工作流 |
| 大重构 | `decisions/` 新增 ADR，`plans/` 新增计划，相关架构文档更新 |

## 六、AGENTS.md 调整方案

AGENTS.md 不应该承载所有细节。它应该是 **AI 执行入口和强约束摘要**。

### 6.1 AGENTS.md 应包含

- 项目一句话说明；
- 当前文档入口；
- 常用命令；
- 最高优先级安全规则；
- 代码分层摘要；
- 常见任务导航；
- 必须同步文档的规则；
- 测试选择规则；
- deploy 目录处理规则；
- 链接到 `standards/` 和 `workflows/`。

### 6.2 AGENTS.md 不应包含

- 长篇架构细节；
- 完整 API 列表；
- 所有配置项说明；
- 已过期历史方案；
- 决策背景长文。

### 6.3 AGENTS.md 与规范文档关系

AGENTS.md 负责“执行时必须立刻知道什么”；`docs/standards/` 负责完整规范。

示例：

```text
AGENTS.md
├── 最高优先级规则
│   ├── 文件删除必须走回收站
│   ├── 源码只改 media_importer/，deploy 不自动同步
│   └── 新配置/新状态/新 API 必须同步文档
└── 规范链接
    ├── docs/standards/coding.md
    ├── docs/standards/testing.md
    ├── docs/standards/configuration.md
    └── docs/workflows/feature-development.md
```

## 七、规范文档设计

### 7.1 `standards/coding.md`

内容：

- Python 文件建议不超过 500 行；
- 单文件超过 500 行必须拆分或在计划中说明原因；
- 函数职责单一；
- 不新增无必要抽象；
- 同子包内优先相对 import；
- 跨子包使用 `media_importer.xxx` 绝对 import；
- 不添加无意义注释；
- CSS 使用变量，不硬编码颜色；
- 前端 JS 按功能模块拆分。

### 7.2 `standards/architecture.md`

内容：

- `api` 是入口层，不承载复杂业务；
- `pipeline` 是编排层，逐步转向调用 services；
- `scraper` 管刮削和元数据；
- `storage` 管文件系统操作；
- `core` 只放基础设施和跨域模型；
- 新业务能力优先有模块文档；
- 大架构变更必须新增 ADR。

### 7.3 `standards/testing.md`

内容：

- 单元测试、集成测试、UI 测试分层；
- 已知失败记录规则；
- 修改范围到测试集合映射；
- Playwright 测试启动服务要求；
- 回归测试矩阵维护方式。

### 7.4 `standards/documentation.md`

内容：

- 文档类型职责；
- 新文档放置规则；
- 旧文档归档规则；
- 链接检查规则；
- 状态标记：`📋 待评审`、`🔄 进行中`、`✅ 已实施`、`🗄️ 已归档`；
- 文档必须说明代码入口和测试入口。

### 7.5 `standards/safety.md`

内容：

- 删除/覆盖影视文件必须走回收站；
- 临时文件可直接删除的边界；
- `allowed_base_dirs` 要求；
- 源文件清理策略；
- deploy 目录不作为自动开发目标。

## 八、工作流文档设计

### 8.1 功能开发闭环

`workflows/feature-development.md`：

```text
1. Brainstorm：明确问题、目标、方案候选
2. Proposal：写 docs/proposals/<feature>.md，说明范围和影响面
3. Architecture/ADR：涉及架构选择时写 decisions/ADR
4. Plan：写 docs/plans/<date>-feat-xxx.md，列任务和验收标准
5. Implementation：按计划实现
6. Test：单元 -> 集成 -> UI/回归
7. Documentation：更新 architecture/modules/standards/INDEX
8. Review：代码和文档一起评审
9. Commit：提交时说明测试结果和文档更新
10. Maintenance：进入定期维护检查
```

### 8.2 重构开发闭环

`workflows/refactor-development.md`：

- 先创建 baseline commit；
- 明确非目标；
- 每阶段保持可运行；
- 每阶段更新文档；
- 不把行为变更混入结构重构；
- 如必须行为变更，单独 ADR。

### 8.3 Bugfix 闭环

`workflows/bugfix.md`：

- 复现；
- 定位；
- 写失败测试；
- 修复；
- 回归；
- 记录解决方案或维护说明。

### 8.4 文档维护闭环

`workflows/documentation-maintenance.md`：

- 月度检查；
- 版本/架构重构后检查；
- 链接和入口检查；
- 已实施方案归档；
- ADR 索引更新。

## 九、决策日志 ADR 设计

### 9.1 ADR 存放位置

`docs/decisions/`

### 9.2 ADR 命名

```text
0001-use-sqlite-json-fields.md
0002-native-js-no-build.md
0003-api-mixin-composition.md
0004-task-lifecycle-centralization.md
```

### 9.3 ADR 模板

```markdown
# ADR-0001: 决策标题

日期：
状态：Accepted | Superseded | Deprecated

## Context

为什么需要决策？

## Decision

做什么选择？

## Consequences

好处、代价、后续约束。

## Alternatives

考虑过什么，为什么没选？

## Links

相关代码、计划、方案、测试。
```

### 9.4 首批需要补齐的 ADR

- SQLite + JSON 字段；
- 原生 HTTP API + Mixin；
- 原生 JS/CSS 无构建；
- YAML 配置 + 自动迁移；
- Provider 抽象；
- 回收站安全删除；
- pipeline 业务服务化；
- 文档体系重构。

## 十、原文档备份方案

执行文档重构前，必须先备份当前 `docs/`：

```text
docs/_archive/2026-05-31-pre-docs-reorg/
```

备份内容：

- 当前所有 `docs/` 下文档；
- 当前 `AGENTS.md`；
- 当前文档文件列表；
- 当前 git commit id。

备份规则：

- 备份后再开始迁移；
- 新文档稳定前不删除旧内容；
- `_archive/` 不作为当前事实引用；
- 后续删除旧文档必须单独评审。

## 十二、验收标准

- AI 能通过 `docs/README.md` 和 `docs/ai-map.md` 定位常见任务修改范围。
- `docs/INDEX.md` 能把代码模块、文档、测试、API 关联起来。
- AGENTS.md 精简为可执行入口，不再承载完整文档内容。
- `standards/` 覆盖代码、架构、测试、文档、安全、配置、API。
- `workflows/` 覆盖功能开发、重构、bugfix、发布、文档维护。
- `decisions/` 有 ADR 索引和首批关键决策。
- 旧文档完整备份，重构完成前不删除。
- 每个架构/模块文档都有“代码入口、扩展点、测试入口、相关规范”。
- 文档结构能支持后续大规模代码重构，而不是阻碍重构。

## 十三、补充建议

1. **文档重构先于代码重构继续推进**：先让 AI 有地图，再动 pipeline/context/lifecycle。
2. **新文档只描述当前事实**：方案和计划不要混入架构事实文档。
3. **每个文档控制篇幅**：单文档建议不超过 500 行；超过则拆分，和代码规范一致。
4. **每个模块文档必须可操作**：必须告诉 AI “改这个模块时看哪些文件、跑哪些测试、更新哪些文档”。
5. **归档不是删除**：先保全历史，再逐步迁移，避免知识丢失。
