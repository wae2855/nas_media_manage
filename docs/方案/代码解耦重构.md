# 代码解耦重构

> **状态：✅ 已实施完成** | 实施日期：2026-05-25
>
> 本方案已完成实施。当前目录结构已按方案重构为子包：api/、core/、monitor/、notify/、pipeline/、scraper/、storage/、webui/。

## Problem Statement

media_importer/ 下 25 个 Python 模块平铺在一个目录中，职责边界模糊、模块间耦合度高，导致：
1. **难以独立理解**：想了解刮削逻辑，需要翻阅 llm_scraper + metadata_scraper + tmdb_client + dimension_manager + classifier 五个文件
2. **难以独立测试**：模块间直接 import，测试时需要 mock 大量依赖
3. **难以独立扩展**：新增置信度引擎模块时，不知道该放在哪里、怎么与现有模块交互
4. **文件定位困难**：25 个文件平铺，新开发者难以快速找到相关代码

## Chosen Approach

## Why This Approach

- **按功能域分组**：每个子包是一个独立的功能域，开发者可以只关注一个子包
- **pipeline 和 api_server 保持原位**：它们是编排层，依赖所有子包，不适合放入任何子包
- **core 是基础设施**：被所有子包依赖，放最底层
- **新增模块有明确归属**：confidence_engine 归 scraper/，文件名清洗器归 scraper/

## Key Design Decisions

### Q1: 子包划分粒度 — RESOLVED

**Decision:** 5 个子包 + 2 个顶层编排模块
**Rationale:**
- 太细（每个模块一个子包）→ 过度设计，import 路径过长
- 太粗（只分 core/business）→ 没有解决"平铺"问题
- 5 个子包是功能域的自然边界：core(基础)、scraper(刮削)、storage(文件)、notify(通知)、monitor(监控)
**Alternatives considered:**
- 3 个子包（core/scrape/business）→ business 太大，仍然混杂
- 每个模块一个子包 → 过度设计

### Q2: import 方式 — RESOLVED

**Decision:** 使用相对 import + 子包 `__init__.py` 导出公共 API
**Rationale:**
- 相对 import 使子包内部解耦，不依赖包名
- `__init__.py` 导出公共 API，外部只需 `from media_importer.scraper import LLMScraper`
- 内部模块用 `from .llm_scraper import LLMScraper`
**Alternatives considered:**
- 绝对 import → 重构时需要改很多路径
- 只用相对 import 不导出 → 外部需要知道内部结构

### Q3: pipeline 和 api_server 的位置 — RESOLVED

**Decision:** 保持原位在 media_importer/ 顶层，但拆分为多个子模块
**Rationale:**
- pipeline 是编排层，依赖所有子包，放入任何子包都会造成循环依赖
- api_server 是 HTTP 入口，也依赖所有子包
- 它们是"胶水代码"，不属于任何单一功能域
- 但两者代码行数过多（2117行、1103行），需要按功能拆分为子模块
**Alternatives considered:**
- 放入 core/ → core 被依赖，不应依赖其他子包
- 新建 orchestration/ 子包 → 只有两个文件，不值得

### Q4: db.py 的归属与拆分 — RESOLVED

**Decision:** 放入 core/，并按功能拆分为 3 个子模块
**Rationale:** db.py 被 task_manager、pipeline、api_server、llm_scraper、dimension_manager 等大量模块依赖，是最底层的基础设施。但 1011 行代码中包含了大量维度默认值（225行）和迁移逻辑（200行），需要拆分。
**Alternatives considered:**
- 单独建 data/ 子包 → 只有 db.py 一个文件，不值得
- 放在 scraper/ → 被所有域依赖，不应放在特定域

### Q5: 兼容性策略 — RESOLVED

**Decision:** 分阶段迁移，每阶段保持系统可运行
**Rationale:** 25 个文件的 import 关系错综复杂，一次性重构风险太大。分阶段迁移，每阶段只移动一个子包的文件，确保测试通过后再继续。
**Alternatives considered:**
- 一次性重构 → 风险太高，可能引入大量 bug
- 不重构 → 问题持续恶化

### Q6: 测试文件的同步 — RESOLVED

**Decision:** 测试文件中的 import 路径同步更新
**Rationale:** 测试文件在 deploy 目录，import 路径需要同步更新。由于当前测试用 `sys.path.insert` 方式，需要调整路径。
**Alternatives considered:**
- 使用 importlib 重定向 → 过于复杂
- 保持旧路径兼容 → 增加维护负担

## 三大文件拆分设计

### db.py (1011行) → core/db/ 子包

**现状分析：**

| 功能块 | 行数 | 说明 |
|--------|------|------|
| DEFAULT_DIMENSIONS | 225行 (L105-L328) | 8 个维度的默认配置，大量 JSON 数据 |
| VALID_STATUSES + 常量 | 5行 | 状态常量 |
| init_db + schema 迁移 | 65行 | 数据库初始化 |
| 维度迁移函数 | 200行 (L430-L604) | 6 个 _migrate_xxx 函数 |
| 维度 CRUD | 105行 (L605-L710) | get/update/enable/disable/reset |
| 任务 CRUD | 195行 (L711-L920) | create/get/list/update/delete |
| 字幕 CRUD | 80行 (L924-L1011) | create/get/update/count |

**拆分方案：**

```
core/db/
├── __init__.py          # 导出所有公共 API
├── connection.py        # init_db, schema 迁移, 连接管理 (~70行)
├── constants.py         # VALID_STATUSES, DEFAULT_DIMENSIONS (~230行)
├── dimension_repo.py    # 维度 CRUD + 维度迁移函数 (~305行)
├── task_repo.py         # 任务 CRUD (~195行)
└── subtitle_repo.py     # 字幕 CRUD (~80行)
```

**关键设计：**
- `constants.py` 中的 DEFAULT_DIMENSIONS 是纯数据，无依赖
- `dimension_repo.py` 依赖 `connection.py` 和 `constants.py`
- `task_repo.py` 和 `subtitle_repo.py` 只依赖 `connection.py`
- `__init__.py` 统一导出，外部无需知道内部拆分

### api_server.py (2117行) → api/ 子包

**现状分析：**

| 功能块 | 行数 | 方法数 | 说明 |
|--------|------|--------|------|
| 基础工具 | 50行 | 3 | json_response, read_json_body, ThreadingHTTPServer |
| 任务 API | 500行 | 15 | _get_task, _retry_task, _confirm_task, _list_tasks 等 |
| 配置 API | 500行 | 12 | _config_save, _config_validate, _config_test_llm 等 |
| 维度 API | 120行 | 7 | _dimensions_list, _dimension_update 等 |
| 提示词 API | 200行 | 6 | _config_save_prompts, _config_reset_prompts 等 |
| 静态文件服务 | 70行 | 1 | _serve_static_file |
| 路由分发 | 200行 | 3 | do_GET, do_POST, do_DELETE |
| 配置工具函数 | 150行 | 7 | _filter_sensitive_fields, _update_config_safely 等 |
| 启动/通知 | 100行 | 3 | start_server, notify_error, on_new_files |

**拆分方案：**

```
api/
├── __init__.py              # 导出 start_server, APIHandler
├── handler.py               # APIHandler 类 + 路由分发 (do_GET/POST/DELETE) (~250行)
├── task_handlers.py         # 任务相关 API 处理函数 (~500行)
├── config_handlers.py       # 配置相关 API 处理函数 + 配置工具 (~650行)
├── dimension_handlers.py    # 维度相关 API 处理函数 (~120行)
├── prompt_handlers.py       # 提示词相关 API 处理函数 (~200行)
├── static_server.py         # 静态文件服务 (~70行)
└── utils.py                 # json_response, read_json_body 等 (~50行)
```

**关键设计：**
- `handler.py` 中的 APIHandler 通过 mixin 模式组合各 handler
- 每个 handler 模块定义一个 Mixin 类，APIHandler 继承所有 Mixin
- 路由分发在 `handler.py` 中统一处理，调用对应 Mixin 的方法

```python
# handler.py
from .task_handlers import TaskHandlersMixin
from .config_handlers import ConfigHandlersMixin
from .dimension_handlers import DimensionHandlersMixin
from .prompt_handlers import PromptHandlersMixin

class APIHandler(TaskHandlersMixin, ConfigHandlersMixin,
                 DimensionHandlersMixin, PromptHandlersMixin,
                 BaseHTTPRequestHandler):
    def do_GET(self): ...
    def do_POST(self): ...
    def do_DELETE(self): ...
```

### pipeline.py (1103行) → pipeline/ 子包

**现状分析：**

| 功能块 | 行数 | 方法数 | 说明 |
|--------|------|--------|------|
| PipelineRunner 核心 | 80行 | 5 | __init__, pause, resume, is_paused, _log |
| scan + process_one | 180行 | 2 | scan_and_create_tasks, process_one |
| confirm + reclassify | 190行 | 2 | confirm_task, reclassify_task |
| 10 个步骤方法 | 500行 | 10 | _step_copy, _step_scrape, _step_validate 等 |
| 辅助方法 | 100行 | 4 | _get_series_dims, _find_cached, _get_import_roots, _get_allowed_dirs |
| 入口 + 异常 | 50行 | 3 | run_all, PipelineError, PipelineSkipError |

**拆分方案：**

```
pipeline/
├── __init__.py              # 导出 PipelineRunner, PipelineError
├── runner.py                # PipelineRunner 核心逻辑 (~260行)
├── steps.py                 # 10 个步骤方法 (~500行)
├── confirm.py               # confirm_task + reclassify_task (~190行)
└── utils.py                 # 辅助函数 + 异常类 (~150行)
```

**关键设计：**
- `runner.py` 定义 PipelineRunner 类，包含核心流程控制
- `steps.py` 中的步骤方法通过 `from .steps import StepsMixin` 以 Mixin 方式组合
- `confirm.py` 中的确认/重分类逻辑独立，因为它们是独立入口（不经过 run_all）

```python
# runner.py
from .steps import StepsMixin
from .confirm import ConfirmMixin

class PipelineRunner(StepsMixin, ConfirmMixin):
    def __init__(self, ...): ...
    def run_all(self): ...
    def process_one(self, task): ...
```

## Open Questions

1. **db.py 中维度默认值的归属**：db.py 中的 DEFAULT_DIMENSIONS 和维度迁移逻辑是否应移到 scraper/dimension_manager.py？这会让 db.py 更纯粹（只管数据存取），但需要处理迁移时的循环依赖。当前方案是放在 core/db/constants.py 中。
2. **前端 JS 中的 API 路径**：前端是否需要调整？应该不需要，因为 API 端点不变。
3. **config.yaml 中的路径**：配置文件中的路径是否需要调整？应该不需要。
4. **Mixin 模式的可读性**：api/ 和 pipeline/ 使用 Mixin 模式拆分，是否会让代码跳转（IDE 中查看定义）变得困难？需要权衡。

## Out of Scope

- API 端点变更 → 不变
- 前端代码变更 → 不变
- 数据库 schema 变更 → 不变
- 功能逻辑变更 → 只做结构重组，不改逻辑
