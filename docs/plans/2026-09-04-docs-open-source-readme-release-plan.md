# 开源项目 README 与公开发布计划

把当前私有 GitHub 仓库整理成信息准确、可安装、可参与且带自愿赞助入口的公开项目，并在公开前完成许可证和敏感信息门禁。

## Problem Statement

根 README 已存在，但仍描述已取消的中心 `temp` 中转和历史能力；GitHub 简介也仍提到已移除的 AI 刮削与 Hermes。仓库当前为私有且没有许可证。直接公开会让读者得到错误产品认知，也可能在完整 Git 历史中暴露不应公开的配置或凭据。

## Target End State

- 根 `README.md` 准确说明项目定位、主要功能、处理流程、fnOS 安装、开发运行、安全边界、贡献和支持方式。
- README 直接引用配置开始页正在使用的收款码与微信二维码，并明确赞助完全自愿、不影响功能。
- 仓库包含用户明确选择的开源许可证。
- 当前工作树及完整 Git 历史通过敏感信息检查，且不包含运行配置、数据库、日志、构建包等私有产物。
- GitHub 仓库简介更新为当前产品事实，仓库切换为公开；默认分支与本地已验证提交一致。

## Scope and Non-Goals

- 本轮修改 README、许可证、需求/验收文档和 GitHub 仓库元数据。
- 复用 `media_importer/webui/assets/support/` 中两个已跟踪二维码，不复制、不重编码、不创建新的支付链接。
- 不发布用户配置、TMDB/API Key、数据库、日志、影片、测试证据或 FPK 二进制到 Git。
- 不承诺商业支持、SLA、百分百自动识别或未经 fnOS 真机确认的兼容性。
- 不重写 Git 历史；若历史审计发现真实凭据，停止公开并先单独处理吊销与历史清理。

## Editorial Contract

- 目标感受：读者在两分钟内理解“它解决什么、是否适合我、如何安装、哪里有风险”。
- 顺序：产品价值 → 功能与边界 → fnOS 使用 → 开发与贡献 → 安全 → 自愿支持。
- 语气：中文为主、事实导向、不过度营销；技术细节只保留到能正确安装和参与开发的程度。
- 二维码必须有清晰替代文本和用途标题；赞助说明放在 README 后半部，不遮蔽安装与安全信息。
- 拒绝标准：仍出现中心 temp 中转、AI 自动刮削、Hermes 等失实表述；把候选 FPK 写成已通过 fnOS 真机验收；二维码路径在 GitHub 上不可渲染；没有许可证就声明“开源”。

## Proposed Solution

以当前 feature/architecture/release 文档为事实源重写 README，使用仓库相对路径嵌入两个二维码。加入许可证后，先执行当前树、历史、忽略规则和大文件检查，再提交并推送。最后通过 GitHub API 更新简介与主题并切换可见性，重新读取公开仓库页面验证 README、图片、许可证与默认分支。

## Acceptance Criteria

- `README.md` 不再包含当前实现相冲突的流程或已移除功能，并能从公开仓库渲染两个二维码。
- 许可证文件存在且 GitHub API 能识别许可证；许可证类型由用户明确授权。
- 高置信凭据模式、私有配置文件和大于发布阈值的异常文件检查无未解释命中。
- `scripts/check_docs.py`、相关静态测试和 `git diff --check` 通过。
- `origin/main` 与本地 HEAD 一致，GitHub 返回 `visibility=PUBLIC`，简介不再提 AI 刮削或 Hermes。

## Decision Rationale

公开仓库会公开完整历史，README 写得漂亮不能替代发布安全审计。二维码直接复用应用内资产可保证品牌与收款入口一致，也避免维护两套图片。许可证是对外授予权利的法律文件，因此不能由实现者默选。

## Risk Analysis

- 公开历史可能暴露已删除凭据：先扫描；发现真实命中立即停止，并要求吊销后再清理历史。
- 收款码可能被第三方替换或滥用：只引用已跟踪原图，提交前后核对哈希和远端路径。
- README 对能力过度承诺：以当前 feature/architecture 文档和 0.3.31 候选状态为准，明确 fnOS 真机验收边界。
- 许可证选错会授予不符合用户意图的权利：许可证未明确前不执行公开切换。

## Publication Blocker

完整历史审计发现多类疑似真实凭据。为避免公开后不可逆泄露，当前仓库保持私有；需要选择“从已审计当前树创建清洁历史的新公开仓库”或“先吊销凭据，再获得授权重写并强推原仓库历史”。
