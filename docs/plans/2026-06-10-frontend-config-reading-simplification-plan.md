# Frontend Config Reading Simplification Plan

一句话：将配置页中的说明型内容从“卡片式说明”统一改造成“文档式说明”，减少边框、弱化容器感、拆分阅读区与操作区，让说明内容更像帮助阅读而不是功能入口。

## 一、Problem Statement

当前配置页已完成黑金影院主题和基础流程组织，但说明型内容仍沿用大量卡片式表达，导致阅读体验与交互语义出现偏差。

已确认的主要问题：

1. `media_importer/webui/index.html` 中的 `开始`、`刮削配置`、`AI 配置`、`入库规则` 页面，存在大量说明卡片、说明列表卡片、卡片内小卡片、子折叠卡片；
2. `media_importer/webui/css/cinema-pages.css` 中 `config-guide-card`、`start-step-card`、`start-directory-card`、`start-alert-card` 等样式都带有明显容器感；
3. `media_importer/webui/css/config.css` 中 `config-collapse-card` 用于 AI 配置时，又与说明卡片叠加，形成“卡片套卡片套折叠”的层级堆叠；
4. 说明内容与真正可操作的表单区域使用了过于接近的视觉语法，用户容易把说明误解成还可以继续点击的功能块；
5. 页面边框和块状底板过多，导致视觉上不够简洁，阅读节奏被切碎。

这不是单纯的“样式太重”，而是信息架构与视觉语义错位：说明内容应该像文档，操作内容才应该像控件区，而当前实现把两者混在了一套容器语言里。

## 二、Target End State

改造完成后，配置页说明区应满足以下状态：

1. 用户一眼能区分“这是说明内容”与“这是可操作区域”；
2. 说明区默认不使用卡片边框，主要依靠标题层级、留白、字重、细分隔线建立结构；
3. 说明区只在必要时保留极轻的提醒样式，不再堆叠多层容器；
4. 表单区保留必要容器感，但比当前更克制；
5. `AI 配置` 中的 `联网搜索增强` 等高级项不再嵌套在说明卡内部，而是作为与表单同级的高级配置区；
6. `开始`、`刮削配置`、`AI 配置`、`入库规则` 的说明区使用统一的阅读型模式；
7. 旧的说明卡片体系不再作为默认新增模式继续扩散。

## 三、Scope

本次计划范围：

1. 配置页说明型内容的视觉与结构统一；
2. 配置页中说明区与操作区的角色分离；
3. 建立统一的阅读型说明样式体系；
4. 替换配置页现有说明卡片模式；
5. 清理不再需要的说明型样式与冗余结构；
6. 补充文档与预览产物，确保后续模型按同一标准执行。

覆盖页面：`开始`、`刮削配置`、`AI 配置`、`入库规则`。

## 四、Non-Goals

本次不包含：

1. 不重做黑金影院主题本身；
2. 不修改胶片流程轨的整体方向；
3. 不新增后端 API 或配置能力；
4. 不顺带重构与本次目标无关的前端逻辑；
5. 不把功能表单也完全去容器化；
6. 不做全站任意页面的风格重写，仅聚焦配置相关说明区；
7. 不以“换一套更轻的卡片”替代“说明区去卡片化”。

## 五、Subjective Contract

这是一次明显带有主观审美目标的改造，执行时必须以“阅读体验”而非“组件感”作为第一优先级。

### 目标感受

1. 页面更安静；
2. 说明更像帮助文档；
3. 说明内容更容易扫读；
4. 只有真正可操作的区域才显得像控件；
5. 视觉上不再到处是块和边框。

### 反目标

1. 不要做成另一套更薄的卡片 UI；
2. 不要把说明写成一整片难以扫描的大段文本；
3. 不要为追求极简牺牲结构感；
4. 不要继续让图标框、hover、投影出现在说明内容上；
5. 不要让新旧两套说明模式长期并存。

### 参考与反参考

正向参考：`media_importer/webui/config-reading-demo.html` 当前第二版极简说明区 demo，以及用户确认的“设置页帮助说明 / 文档式阅读区”方向。

反向参考：当前 `config-guide-card` 组合、`start-step-card` / `start-directory-card` 并列小卡片、`AI 刮削说明` 卡 + 子折叠 `联网搜索增强` 的嵌套模式。

### Representative Proof Slice

先以 `AI 配置` 作为代表性验证切片：

1. `AI 刮削` 说明区去卡片化；
2. `AI 辅助` 说明区去卡片化；
3. `联网搜索增强` 从说明区内部子卡片提升为同级高级项；
4. 表单区与说明区层次明确分离。

只有这个切片满足目标体验后，才推广到其他页面。

### Rollout Rule

1. 先建立统一说明样式体系；
2. 再改 `AI 配置`；
3. 经视觉确认后，再推广到 `开始`、`刮削配置`、`入库规则`；
4. 最后统一清理旧说明卡样式。

### Rejection Criteria

满足以下任一情况即视为结果不合格：

1. 说明区仍然大量使用边框或块状卡片；
2. 说明项仍然看起来像可以点击的功能入口；
3. 高级项仍然嵌套在说明卡内部；
4. 虽然减少了卡片，但说明结构变得难以扫描；
5. 表单区与说明区的视觉差异仍不明显。

## 六、Proposed Solution

核心方案：建立一套“阅读型说明体系”，并将配置页中的说明区统一迁移到这套体系下。

### 6.1 说明区与操作区完全分层

说明区默认无边框、无 hover、无图标按钮感，主要通过标题、段落、留白、细分隔线组织信息。

操作区保留输入框、开关、按钮、测试行为，可继续使用 `form-card` 一类容器，但需减轻边框与背景强度，并与说明区保持清晰节奏切换。

### 6.2 统一说明组件模型

建议建立以下结构，不要求一定使用这些类名，但必须保证语义一致：

1. `info-intro`
   - 用于页头说明；
   - 结构：标签/眉题 + 标题 + 一段简介；
   - 不用边框。

2. `info-rows`
   - 用于结构化阅读；
   - 结构：左侧短标签，右侧标题 + 正文；
   - 行间使用极淡 `border-top` 分隔。

3. `info-callout`
   - 用于强调提醒；
   - 结构：短标题 + 一句或两句正文；
   - 只允许一条左侧强调线，必要时使用极淡背景；
   - 不使用完整描边框。

4. `advanced-disclosure`
   - 用于高级项；
   - 与说明区同级，不嵌套在说明内部；
   - 只负责低频功能收起，不负责承载普通说明。

5. `form-section`
   - 用于真实可编辑表单；
   - 保留容器感，但弱化视觉重量。

### 6.3 统一视觉规则

执行中必须严格遵守：

1. 阅读区默认无描边；
2. 阅读区默认不使用块状底板；
3. 分组优先级为：留白 > 标题层级 > 字重 > 细分隔线 > 少量强调色 > 极淡背景；
4. 阅读区不使用 hover 动效；
5. 阅读区不使用抬升、发光、投影等可交互暗示；
6. 图标仅在确有必要时出现，且不能使用“图标方块”样式；
7. 每一段说明区最多只允许一个提醒型强调块；
8. 表单区的描边和背景也应同步减轻，避免说明区变轻后表单区显得过重；
9. 移动端下 `info-rows` 必须自动收敛为单列上下结构。

## 七、Page-by-Page Mapping

### 7.1 开始页

现状问题：

1. 三步说明被拆成三张小卡；
2. 六个目录说明被拆成六张小卡；
3. 首次提醒是一个大卡里嵌套多条提醒；
4. “跑通之后再做什么”仍是三块说明卡。

改造方案：

1. 顶部使用一个 `info-intro`；
2. `三步完成基础配置` 改成 `info-rows`；
3. `首次使用先记住这三条` 改成一个 `info-callout` + 简短分点文本，或单组 `info-rows`；
4. `这 6 个目录各管什么` 改成结构化术语行，不再做六个卡片；
5. `跑通之后再做什么` 改成简洁说明列表，不再做并列卡片。

### 7.2 刮削配置页

现状问题：

1. “这一页先做什么”被做成说明卡组；
2. “元数据源配置”又单独是一张说明卡；
3. 说明区和 Provider 功能区之间边界不够明确。

改造方案：

1. 页面顶部只保留一个 `info-intro`；
2. `先启用 Provider / 再填写凭据 / 最后测试连通性` 改成 `info-rows`；
3. “元数据源配置”卡删除，信息并入 intro；
4. Provider 列表保留功能容器身份。

### 7.3 AI 配置页

现状问题：

1. `AI 刮削` 内部先是折叠卡，再放说明卡，再放子折叠卡；
2. `AI 辅助` 内部同样有说明卡；
3. 说明信息和字段表单都长在同一容器层次下，角色不清。

改造方案：

1. `AI 刮削`
   - intro：解释用途与适用场景；
   - rows：不开启时 / 开启后 / 模型要求；
   - callout：关键提醒；
   - form：API Key、Base URL、模型、超时、重试等；
   - advanced-disclosure：联网搜索增强。

2. `AI 辅助`
   - intro：解释为何必填；
   - rows：为什么必填 / 不需要联网搜索 / 模型要求低；
   - form：辅助模型、地址、Key、清理模型。

3. 必须去掉：
   - `AI 刮削说明` 说明卡；
   - `AI 辅助说明` 说明卡；
   - `联网搜索增强` 作为说明区内部子卡片的结构。

### 7.4 入库规则页

现状问题：

1. 顶部说明仍偏卡片式；
2. 说明区与规则功能区之间节奏不够克制。

改造方案：

1. intro：解释规则匹配顺序；
2. rows：顺序优先 / 具体规则在前 / 命名变量策略；
3. callout：拖拽调整优先级与权限提醒；
4. 规则列表继续保留功能容器身份。

## 十、Decision Rationale

### D1：为什么不是“优化卡片”，而是“说明区去卡片化”

因为用户已经明确指出，即便弱化卡片，只要说明内容仍大量依赖边框和块状容器，视觉层次仍然会显得过多。继续优化卡片只会得到“更轻一点的卡片堆叠”，不会真正解决阅读语义错位。

### D2：为什么保留表单容器感

因为说明区和操作区需要角色分离。若所有内容都去容器化，用户反而难以识别哪部分可以编辑、保存、测试。正确做法不是“全都极简”，而是“只让说明极简，让操作保留足够可操作感”。

### D3：为什么先做 AI 配置 proof slice

因为 `AI 配置` 同时具备：

1. 说明内容最多；
2. 嵌套最复杂；
3. 高级项折叠最明显；
4. 最能代表本次问题。

在这里验证成功，推广成本最低，偏航风险也最小。

### D4：为什么需要统一说明体系而不是逐页临时改

如果逐页按感觉改，很快会长出新的不一致：某页是轻卡片，某页是分隔线，某页又是图标行。统一说明体系能把这次主观改造收敛成明确模式，方便后续模型稳定执行。

## 十一、Constraints and Boundaries

1. 前端仍为原生 HTML/CSS/JS，无构建依赖；
2. CSS 应继续使用变量体系，避免新硬编码色值扩散；
3. 本次目标是结构与视觉语言调整，不应混入不必要的功能逻辑变更；
4. 不修改 deploy 副本；
5. 不把说明区样式写成只适配单页的临时 hack；
6. 文档建议控制在单文件可维护范围内，避免再生成超大说明文档。

## 十三、Risk Analysis

### Risk 1：JS 依赖旧结构或旧类名

风险：折叠、保存、测试、状态展示逻辑可能依赖旧 DOM。

缓解：

1. 替换前先全局搜索选择器；
2. 优先保持字段 ID 与功能入口不变；
3. 结构调整后做最小行为回归。

### Risk 2：新说明区过于极简，失去扫描性

风险：虽然边框减少了，但信息变成大段文本，不利于快速浏览。

缓解：

1. 用 `info-rows` 维持结构化阅读；
2. 每段说明限制在短句和短段落；
3. 每页保留一个提醒型强调块即可。

### Risk 3：只改局部页面，导致新旧风格长期并存

风险：页面体验更割裂。

缓解：

1. proof slice 验证后尽快推广到四个核心页面；
2. 收尾阶段统一清理旧样式。

### Risk 4：表单区相对显得过重

风险：说明区变轻以后，表单容器显得突兀。

缓解：

1. 同步减轻 `form-card` 强度；
2. 仅保留必要的边界感，避免新的失衡。

### Risk 5：执行者把目标误解为“去掉所有块状结构”

风险：操作区和说明区一起被削平，导致可用性下降。

缓解：

1. 在计划中明确区分“说明区去卡片化”和“表单区保留容器感”；
2. 明确 rejection criteria。

## 十四、Acceptance Criteria

1. 配置页主要说明区不再出现“卡片套卡片”模式；
2. `开始` 页不再使用大量并列说明小卡片；
3. `刮削配置` 页顶部说明从卡片式改为阅读型结构；
4. `AI 配置` 页中 `AI 刮削说明` 与 `AI 辅助说明` 不再使用说明卡；
5. `AI 配置` 页中 `联网搜索增强` 不再作为说明区内部子卡片嵌套存在；
6. `入库规则` 页顶部说明与其他配置页保持同一说明模式；
7. 说明区的边框数量、背景块数量相较当前明显减少；
8. 说明区默认无 hover、无升起、无功能图标框；
9. 表单区与说明区有明确视觉角色差异；
10. 桌面端与移动端下说明区都保持可读、可扫描；
11. 配置保存、测试权限、测试连通性、折叠展开等现有交互不回归。

## 十五、Required Preview Artifacts

在正式推广前，至少需要以下预览材料：

1. `AI 配置` 真实页面改造前后截图；
2. `开始` 页面真实改造后截图；
3. 移动端窄宽度下的说明区截图；
4. 若有必要，补一份简单结构对照说明，明确新旧说明模式替换关系。

## 十六、Execution Notes For Another Model

交给其他模型执行时，建议附带以下硬约束：

1. 不要从全站大改开始；
2. 先完成 `AI 配置` proof slice；
3. 先确认说明体系与结构模式，再逐页推广；
4. 不允许用“更轻的卡片”替代“说明区去卡片化”；
5. 不允许继续把高级项嵌套在说明内容内部；
6. 不要修改字段 ID、主要交互入口和配置保存逻辑语义；
7. 替换前先搜索 JS 是否依赖旧类名或折叠结构；
8. 收尾时必须清理旧说明卡样式，避免双轨长期并存。
