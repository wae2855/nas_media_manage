# 存储检查与配置检查职责分离

- **Requirement**: [REQ-20260831-214244](../tracking/requirements-board.md)
- **Proposal**: [检查职责与目录操作边界](../proposals/2026-08-31-config-check-separation.md)
- **Status**: pending_acceptance

让“存储检查”只回答目录是否可访问，让最后一步“配置检查”统一回答规则、片库、外部能力和自动运行是否可以开始。

## Problem Statement

当前存储检查会平铺“旧规则待设置”和逐条规则异常，把物理目录健康与业务分流配置混在同一页面；旧配置用户还会被目录选择弹窗直接带到片库整理。用户无法稳定理解“这一页到底检查目录，还是检查规则”。完成页已有统一启动就绪检查，但按钮和结果仍使用“开场检查”术语，规则异常的“去处理”也没有正确跳到片库整理。

目录权限还需要冻结为产品操作边界。POSIX 目录写权限不能证明“可新增但不可删除”，因此片库保护不能依赖 ACL 文案或写入探针，而必须由业务文件操作白名单保证。

## Target End State

- 存储检查只显示来源、回收、日志、缓存和 0～N 个片库目录的路径、授权、读写、挂载与容量结论；中心中转角色已由 ADR-0022 删除。
- 未绑定、引用不存在或停用片库的规则只在最后一步“配置检查”中作为阻塞项展示，并可准确跳到“片库整理”。
- “运行开场检查”统一改为普通用户更容易理解的“配置检查”。
- 片库整理页面、规则编辑与显式 `library_root_id` 保存行为保持不变。
- 目录角色操作矩阵成为安全规范：片库只允许读取和新增入库；通用删除、清理、改名和覆盖均禁止，唯一替换例外继续要求用户逐项确认、指纹复核并先进入本地回收。

### Target outcome

用户在存储检查看到的是一组干净、可操作的目录健康卡；只有到最后一步主动点击一次“配置检查”，才看到跨模块的完整能否运行结论。

### Anti-goals

- 不把规则列表换一种样式继续塞在存储检查或目录选择弹窗里。
- 不让系统按片库顺序、默认根或旧路径猜测规则归属。
- 不新增另一套与 `inspect_startup_readiness` 漂移的前端校验。
- 不声称文件系统 ACL 能单独提供“允许新增但禁止删除”的权限。

## Scope and Non-Goals

### In scope

- 移除存储检查和片库选择弹窗中的旧规则明细、规则跳转与迁移专属引导。
- 片库根继续支持独立添加、授权、保存和动态扩充。
- 完成页按钮、空态、成功、失败和提示统一使用“配置检查”。
- 配置检查的规则项明确覆盖根存在、启用、目录可访问及写入能力；修复入口跳到片库整理。
- 同步安全、配置、存储架构、前端信息架构、需求和测试文档。

### Non-goals

- 不改变片库整理页面结构和规则编辑弹窗。
- 不改变 Provider、LLM、自动运行和目录 readiness 的既有判断条件。
- 不放宽任何片库文件保护或目录拓扑边界。
- 不在本轮生成、发布或上传 FPK；真机包在用户确认页面后另行生成。

## Proposed Solution

1. `renderStorageReadiness()` 始终只渲染目录卡和普通“添加目标片库”入口，不读取或展示规则关联异常。
2. 片库新增弹窗统一为“确认目录并保存”，移除暂存、规则明细和保存后自动跳转；旧规则仍可保持待完成状态。
3. 保留后端 `canonicalize_library_config(..., require_rule_assignments=True)` 作为最终规则事实源；在配置检查中把规则绑定与其目标目录健康组合成用户可理解的“规则与目标片库”结果。
4. UI 继续调用现有只读 `/config/startup-readiness` API，但所有用户可见术语改为“配置检查”；内部端点和函数名保持稳定。
5. 在安全标准中新增角色能力矩阵，并明确片库禁止删除依靠业务硬边界而非 POSIX ACL。

## Decision Rationale

- 存储目录和入库规则是两类独立事实，分开编辑、最后聚合验收比在中途互相跳转更容易理解。
- 复用既有 startup readiness 可确保手工运行、自动运行和界面检查使用同一事实源。
- 片库写权限是新增入库的必要条件，但目录写权限同时可能允许删除；因此安全承诺必须由文件操作入口限制，而不能用权限测试替代。

## Constraints and Boundaries

- 目标片库已有文件默认只读；正常运行只新增。
- 用户逐项确认替换仍是唯一可处置同名旧文件的路径，旧文件必须先进入本地回收，禁止永久删除兜底。
- 来源的写/清理能力只在所选来源处理策略需要时成为 readiness 必需项。
- 回收、日志和缓存只能删除本应用可证明归属的对象。
- 存储检查保存片库根时不得要求规则已经完成绑定。

## Assumptions

| Assumption | Status | Evidence |
|---|---|---|
| 最终检查已经校验规则根存在和启用 | Verified | `startup_readiness.py` 调用 `canonicalize_library_config(..., require_rule_assignments=True)` |
| 最终检查已经取得每个启用片库的目录健康 | Verified | `inspect_storage_readiness()` 输出 `target:<root_id>` 位置记录 |
| 片库根可在规则未完成时独立保存 | Verified | `config_save.py` 仅在保存规则字段时要求规则绑定 |
| 片库写权限可通过 ACL 单独禁止删除 | Rejected | POSIX 目录写权限同时控制创建和删除；必须依靠业务操作边界 |

## Risk Analysis

| Risk | Mitigation |
|---|---|
| 移除迁移 callout 后无法保存已选择片库 | 取消“暂存”中间态，每次选择都走普通片库保存流程 |
| 规则异常只在最后出现，用户不知道去哪修复 | 配置检查结果保留规则名称与原因，“去处理”明确跳到片库整理 |
| 文案改名但错误提示仍出现“开场检查” | 对完成页渲染、Toast、API message 和活跃文档做定向文本检查 |
| 写权限探针被误解为片库可删除 | 文档区分物理能力与产品允许操作；保留片库文件动作白名单测试 |

## References and Design Contract

- 正向参考：现有完成页分项检查卡、存储目录健康卡、胶卷阶段导航。
- 反向参考：用户截图中存储检查平铺七条规则的高密度 callout。
- 视觉规则：不新增醒目警告卡；存储页保持目录卡单一节奏；最终结果继续使用现有黑金检查卡和中文状态。
- Representative proof slice：旧规则未绑定时，存储检查只显示目录卡；点击“配置检查”后显示“规则与目标片库：需要处理”，并可跳到片库整理。
- Rollout rule：桌面 1440px 和移动 390px 的 proof slice、配置专项与 readiness 测试通过后才视为完成。
- Rejection criteria：存储检查或目录弹窗仍出现规则明细；规则错误跳错页面；规则缺失仍能通过配置检查；任何通用入口获得删除片库文件能力。
- Required previews：旧规则场景的存储检查截图、完成页配置检查阻塞截图，桌面与移动端各一次布局检查。

## Acceptance Criteria

1. 配置包含未绑定、未知或停用片库规则时，存储检查不显示规则异常、旧规则 callout 或“去设置规则”按钮。
2. 同一配置点击“配置检查”后返回 BLOCKED，结果包含规则名称/序号和原因，“去处理”进入片库整理。
3. 所有规则绑定有效片库且相关目录存在、授权、可读并具备新增能力时，规则与目标片库检查通过。
4. 存储检查仍可独立添加任意数量片库、重新授权、编辑和移除，不因旧规则状态丢失保存入口。
5. 完成页所有用户可见文案统一为“配置检查”，不再出现“开场检查”。
6. 片库整理页面和规则保存行为没有结构或语义变化。
7. 安全标准明确六类目录的读、写、删除边界，并说明片库删除禁令由业务白名单实现。
8. 桌面、移动 proof slice 与相关自动化、架构、静态和文档检查通过。
