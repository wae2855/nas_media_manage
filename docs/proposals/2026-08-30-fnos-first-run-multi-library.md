# fnOS 首次启动目录授权、多片库与离线依赖提案

## 问题（现状与痛点）

安装时等待 Python 缺少可见进度，应用依赖还可能再次联网安装；片库只允许一个根，无法覆盖多硬盘；原生向导只能手填目录，不能浏览和完成 fnOS 授权。

## 目标（可验证）

- 保持官方 `python312` 依赖，项目 Python 依赖从 FPK 离线安装。
- 支持多个片库根，并让每条整理规则明确归属某个片库。
- 首次 Web 启动调用 fnOS 共享目录选择/授权，普通浏览器保留手动输入。
- 旧单根配置无损迁移；所有目录和规则继续执行服务端安全校验。

## 方案概述（推荐方案 + 关键取舍）

配置以 `library_roots[]` 为事实源，根使用稳定 ID，规则和兜底目录保存 `library_root_id + relative template`。运行时只在选中根下解析目标。

安装向导只采集端口/API Key 并说明“目录在首次启动选择”。Web 首次启动按角色请求 fnOS 授权：来源和片库可选远程挂载，回收只展示本地共享目录。开放能力不可用时降级为手填，但最终检查不会降级。

构建阶段生成架构对应的 wheelhouse，FPK 安装时使用 `--no-index`。系统 `python312` 的首次安装仍由 fnOS 管理，应用日志明确记录随后各阶段。

## 影响面（代码/配置/API/测试/文档）

- 配置 loader、迁移、validator、ConfigView、保存 API。
- 分类、允许目录、存储就绪和多根容量检查。
- 配置胶卷的片库根列表、规则根选择、首次启动目录按钮。
- fnOS manifest/resource/install scripts、开放 API 适配器和离线 wheel 构建。
- 旧配置迁移、路径逃逸、远程掉线、UI 双端、FPK 安装回归。

## 备选方案（为何不选）

- 内嵌完整 Python：偏离官方依赖管理且多架构维护成本高。
- 继续单根并要求用户建统一上级目录：跨卷不可行。
- 规则保存任意绝对路径：破坏授权边界和运行时 containment。
- 安装向导继续手填：无法提供浏览和授权，也不能消除路径错误。
