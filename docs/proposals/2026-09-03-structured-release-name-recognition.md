# 结构化发布名识别与 Provider 身份校验

## 问题（现状与痛点）

当前自研解析器把通用发布名语法、中文下载站噪声和具体片名例外混在同一组正则中。fnOS 实测中，`Carry.Me` 被误删为广告域名，`第一季` 未从剧名中剥离，`EP01-05` 未表达为范围，导致正确 TMDB 候选仍需确认或完全搜不到。继续追加片名例外会扩大误伤和维护成本。

## 目标（可验证）

- 使用成熟通用解析器提取国际 Scene/PT 发布名字段，自研代码只承担中文语法和产品证据融合。
- 文件名、可信目录、TMDB 标题/原始标题/官方别名分别保留证据，不把字符串简单拼接后猜测。
- 证据充分才自动通过；识别失败或冲突时在复制前进入人工确认。
- fnOS 当前《极地重生》《北海鲸梦》以及英文 `.me` 片名样本形成永久回归语料。

## 方案概述（推荐方案 + 关键取舍）

引入固定版本 GuessIt 作为通用发布名解析底座；在其前后增加薄层中文规范化和结果归一化。TMDB Provider 增加官方别名读取能力，匹配引擎只在标题、年份、类型和官方别名形成闭环时自动通过。目录只作为受控辅助证据，剧集范围不会覆盖单文件的具体集号。

不把 GuessIt 的输出直接视为媒体身份，也不为具体影片建立白名单。可变的站点噪声后续通过独立、可测试的识别词机制扩展，本次不增加复杂配置界面。

## 影响面（代码/配置/API/测试/文档）

- 依赖与 fnOS 离线 wheelhouse：`requirements.txt`、`deploy/requirements-fnos.lock`、打包校验。
- 刮削：发布名解析、目录证据、Provider 别名验证、匹配轨迹。
- 测试：真实语料、Provider mock、流程门禁和现有匹配回归。
- 文档：刮削架构、功能入口、匹配标准和测试矩阵。

## 备选方案（为何不选）

- 继续扩展自研正则：短期快，但具体片名与域名规则会持续冲突。
- 完全依赖 GuessIt：中文数字季、国内字幕/广告语料覆盖不足，不能单独承担身份判断。
- 复制 Sonarr/Radarr 解析代码：与其数据模型耦合，并增加许可证与长期同步成本。
