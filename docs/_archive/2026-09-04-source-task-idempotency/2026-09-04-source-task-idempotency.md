# 来源任务幂等创建加固方案

## 问题（现状与痛点）

扫描入口采用“先判重、后创建”，并发时存在窗口；手动单文件入口则直接创建任务。两者叠加后，同一来源可能生成多条任务。扫描已有来源证据没有随新任务统一写入，使后续变化判断不完整。

## 目标（可验证）

- 同一真实来源路径无论由扫描、手动还是并发触发，最多新增一条任务。
- 重复请求复用既有任务并返回任务 ID，不启动重复处理。
- 新任务在创建时保存来源指纹、字节大小和修改时间。
- 失败任务保持原记录，只有用户显式重试才重新排队。

## 方案概述（推荐方案 + 关键取舍）

在 `TaskManager` 建立单一的原子“创建或复用”入口，在进程锁内完成真实路径归一化、重复判定、证据更新和新任务创建。批量扫描与手动单文件服务都只能通过该入口创建普通来源任务。

所有活动任务、失败任务，以及来源未变化的成功/跳过/取消任务均复用。文件大小发生明确变化时沿用重新处理语义；仅修改时间变化时只刷新证据。

现有来源指纹是 `size + mtime` 的短摘要，不具备内容身份强度。本轮不据此自动合并不同路径下的失败任务；仅用真实路径归一化收敛符号链接等可证明是同一对象的别名。

## 影响面（代码/配置/API/测试/文档）

- 代码：任务管理器、任务数据库创建参数、扫描创建、手动单文件服务。
- API：重复手动请求返回冲突和既有任务信息，不再启动后台线程。
- 配置/数据库：不新增配置，不迁移表结构，复用现有来源证据字段。
- 测试：状态判重、并发原子性、入口竞争、证据持久化、真实路径别名。
- 文档：任务、导入流程、生命周期和回归矩阵。

## 备选方案（为何不选）

- 数据库 `source_path` 唯一键：历史表允许同一路径在文件明确变化后形成新审计任务，直接唯一约束会破坏该能力。
- 按弱指纹跨路径自动合并：不同影片可能恰好大小和修改时间相同，误合并风险高。
- 自动删除历史重复记录：会破坏审计与用户已处理结果，交由用户核对后显式删除更安全。
