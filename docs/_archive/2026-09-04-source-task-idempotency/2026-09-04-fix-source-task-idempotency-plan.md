# 来源任务幂等创建加固计划

将扫描、手动单文件等入口统一到一个原子“创建或复用”入口，确保同一来源在重复触发和并发触发下不会生成重复任务，并保留可解释的来源文件证据。

## 问题与目标

- 当前批量扫描先检查、后创建，两个动作之间存在并发窗口；手动单文件入口还会绕过去重直接创建任务。
- 扫描阶段已经计算来源指纹、大小和修改时间，但创建任务时没有统一持久化，后续判定缺少发现时证据。
- 已失败任务应保持为同一个待处理对象，由用户显式重试，不应因为再次扫描或再次点击而增加一条失败记录。
- 已成功、跳过或取消且来源未变化的任务也应复用，避免保留来源文件时反复入队。

## 范围与取舍

- 在单进程任务管理器内，用同一把锁完成重复判定和任务创建；这符合当前 fnOS 单实例部署模型。
- 新建任务统一保存 `source_fingerprint`、`source_file_size`、`source_mtime`，复用现有数据库字段，不新增迁移。
- 新入口统一使用规范化真实路径，收敛 `.`、`..`、符号链接等同一文件别名。
- 现有 `size + mtime` 指纹只作为辅助证据，不用于把不同路径下的失败任务自动合并；真实改名或挂载点变化继续保守地视为新来源。
- 不删除、不合并历史重复任务，不改变任务状态枚举，不自动重试失败任务，不增加前端配置。

## 任务分解

- [x] 注册需求与一页方案，明确历史记录保留和跨路径保守边界。
- [x] 在任务管理器增加原子“创建或复用来源任务”能力，并统一规范化路径和来源证据写入。
- [x] 修正重复判定：所有待处理状态、失败状态，以及来源未变化的成功/跳过/取消状态均复用现有任务。
- [x] 批量扫描改用统一入口，使扫描过滤只承担性能优化，最终一致性由任务管理器保证。
- [x] 手动单文件 API 在启动后台处理前同步执行统一入口；重复请求返回现有任务信息且不启动第二个工作线程。
- [x] 增加并发、重复扫描、手动入口、终态复用和证据持久化测试。

## 测试计划

- 单元测试：多线程同时创建同一路径，断言仅一条任务且所有调用返回同一任务 ID。
- 单元测试：新任务持久化指纹、大小、修改时间；真实路径别名复用同一任务。
- 状态测试：`PENDING`、`FAILED`、来源未变化的 `SUCCESS/SKIPPED/CANCELLED` 均不新增任务；明确变化后的终态按既有规则重新处理。
- 集成测试：同一路径连续扫描不新增任务；扫描和手动入口竞争时仍只有一条任务。
- API 测试：重复手动提交返回可解释的冲突结果，并验证处理器未被第二次调用。
- 质量命令：相关 pytest、架构护栏、改动文件 ruff、compileall、文档检查，最后执行完整 pytest 回归。

## 验收标准

- 同一真实来源路径在扫描、手动、并发混合触发下，数据库最多新增一条任务。
- 重复请求能返回既有任务 ID、状态和原因，不启动重复刮削或文件处理。
- 来源发现证据在任务创建时完整保存，后续修改判定不再依赖空字段。
- 已有任务历史不被自动删除或重写，显式重试流程保持可用。
- 相关测试、架构护栏、文档检查和完整回归全部通过。

## 风险与缓解

- 锁内数据库操作可能稍微延长创建阶段临界区；只覆盖轻量判定和单条创建，不包裹刮削与复制。
- 真实路径归一化可能让新任务展示规范化后的路径；保留原始文件名，且只对后续新建任务生效。
- 多进程同时写库不在本轮保证范围；当前 fnOS 单实例运行成立，未来若支持多实例需使用数据库唯一键或租约进一步约束。
- 弱指纹跨路径碰撞风险高，因此本轮宁可产生一次需要人工处理的新来源，也不自动错误合并两部影片。
