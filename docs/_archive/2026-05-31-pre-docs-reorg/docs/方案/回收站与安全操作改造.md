## 一、改造目标

| # | 需求 | 核心原则 |
|---|------|---------|
| 1 | 源文件删除可配置 | 新增 `delete_source_after_import` 开关，默认 true 保持现有行为 |

## 三、改造方案

### 3.1 需求1：源文件删除可配置

#### 配置设计

```yaml
source_policy:
  delete_source_after_import: true   # 入库成功后是否删除源文件
                                     # true  - 删除源文件（现有行为）
                                     # false - 保留源文件不动
```

#### 改动清单

| 文件 | 改动 |
|------|------|
| `config_loader.py` | `source_policy.setdefault("delete_source_after_import", True)` |
| `steps.py` `_step_import()` | 包裹 `delete_source_with_companions()` 调用 |
| `steps.py` `_step_import_from_confirm()` | 同上 |
| `config.yaml` | source_policy 下新增配置项和注释 |
| `config.js` | 前端源策略区域增加开关 |
| `config_handlers.py` | 配置保存/读取支持新字段 |

#### 核心代码变更

```python
# steps.py _step_import() 中
source_policy = self.config.get("source_policy", {})
if source_policy.get("delete_source_after_import", True):
    if source_dir and original_source_video:
        delete_source_with_companions(...)
        remove_empty_parent_dir(...)

    self._log("info", "源文件保留（配置: delete_source_after_import=false）", task, "import")
```

#### 注意事项

- 中转临时文件的清理不受此开关影响，始终删除

- 源文件保留后，下次扫描可能重新发现，需依赖 `source_policy.dedup_enabled` 去重

### 3.2 需求2：回收站改造

#### 核心原则

**所有删除/覆盖操作 → 移入回收站**，不再有任何直接删除。

#### 回收站目录结构

```
{recycle_dir}/
├── 2026-05-28/                    # 按日期组织
│   ├── Inception.2010.1080p.mkv   # 被替换的旧文件
│   ├── Inception.2010.1080p.mkv.meta  # 元信息
│   ├── source_abc123/             # 源文件删除（按task_id分组）
│   │   ├── movie.mkv
│   │   └── movie.srt
│   └── ...
└── 2026-05-29/
    └── ...
```

#### .meta 元信息文件格式

```json
{
  "original_path": "/vol1/影视/电影/2010/Inception (2010)/Inception.2010.1080p.mkv",
  "reason": "dedup_replace",
  "task_id": "abc123",
  "moved_at": "2026-05-28T14:30:00",
  "file_size_mb": 12345.6,
  "source_title": "盗梦空间",
  "provider_type": "tmdb",
  "provider_id": "27205"
}
```

reason 取值：
- `dedup_replace` — 去重替换
- `quality_replace` — 质量优先替换
- `source_cleanup` — 入库后源文件清理
- `temp_cleanup` — 临时文件清理
- `import_overwrite` — 入库目标覆盖
- `cross_device_move` — 跨设备移动源文件清理

#### 新增工具函数

```python
# safety.py 新增
def move_to_recycle(src_path: str, recycle_dir: str,
                    reason: str = "", task_id: str = "",
                    extra_meta: dict = None) -> tuple:
    """
    将文件安全移入回收站。
    返回 (success: bool, dest_path: str, message: str)
    """
```

功能要点：
1. 安全校验：路径穿越检查、文件类型白名单
2. 日期子目录：`recycle_dir/YYYY-MM-DD/`
3. 同名冲突：自动加序号 `_1`, `_2`
4. 跨设备支持：先 `shutil.copy2()` 再删除源文件
5. 写 `.meta` 侧文件记录来源信息
6. 附属文件（字幕）跟随主文件移入同目录

## 四、源端文件增删改场景方案

### 4.1 文件指纹设计

#### 指纹定义

文件指纹 = `f"{file_size_bytes}:{mtime_timestamp}"` 的 SHA256 哈希前16位

```
示例：文件 1,610,612,736 字节，mtime 1748390400.0
指纹 = sha256("1610612736:1748390400.0")[:16] = "a3f8c2e91b7d4506"
```

**为什么用 size + mtime 而不是文件内容哈希？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 文件内容 MD5/SHA256 | 精确，改名也能识别 | 大文件（10GB+）计算耗时数分钟 |
| **size + mtime 哈希** | 瞬间完成，改名/移动可识别 | 极小概率碰撞（不同文件恰好同大小同时间） |
| 纯 size | 最快 | 碰撞概率高 |

size + mtime 是最佳平衡：对于影视文件（GB级），同大小同修改时间几乎不可能是不同文件。

#### 指纹存储

tasks 表新增 `source_fingerprint` 列：

```sql
ALTER TABLE tasks ADD COLUMN source_fingerprint TEXT DEFAULT '';
```

创建索引加速查找：

```sql
CREATE INDEX IF NOT EXISTS idx_tasks_fingerprint ON tasks(source_fingerprint)
```

#### 指纹生成时机

```
FileScanner 扫描源目录
  → 发现视频文件
  → 计算 source_fingerprint = make_fingerprint(file_path)
  → 调用 check_source_duplicate(source_path, source_fingerprint)
  → 创建任务时写入 source_fingerprint
```

```python
def make_fingerprint(file_path: str) -> str:
    import hashlib
    stat = os.stat(file_path)
    raw = f"{stat.st_size}:{stat.st_mtime:.1f}"
    return hashlib.sha256(raw.encode()).hexdigest()[:16]
```

#### 指纹匹配流程

```
L1: source_path 精确匹配（现有逻辑）
  ↓ 未命中
L2: source_fingerprint 匹配（新增，走索引）
  ↓ 未命中
L3: 创建新任务（真正的新文件）
```

### 4.2 六大场景详解

#### 场景A：文件改名（同内容，新文件名）

```
之前：/source/Inception.2010.1080p.mkv  fingerprint=a3f8c2e91b7d4506  → 已入库 SUCCESS
现在：/source/盗梦空间.2010.1080p.mkv   fingerprint=a3f8c2e91b7d4506  → 同一文件改了名
```

**检测**：L1 路径不匹配 → L2 指纹匹配命中 → RENAME_DETECTED

**处理**：
- 更新历史任务的 `source_path` 为新路径
- 跳过重复入库，日志记录"文件改名，已更新路径引用"
- 这是 `delete_source_after_import=false` 时最常见的场景

#### 场景B：文件修改日期变了（同名，内容可能变）

```
之前：/source/movie.mkv  size=1.5GB  mtime=05-20  fingerprint=abc123  → 已入库 SUCCESS
现在：/source/movie.mkv  size=1.5GB  mtime=05-28  fingerprint=def456  → 同名但时间变了
```

**检测**：L1 路径匹配命中 → 指纹不同 → 文件有变化

**关键判断**：size 是否变了？

| 变化 | 可能原因 | 处理 |
|------|---------|------|
| 仅 mtime 变，size 不变 | BT做种时间漂移/文件系统缓存 | UPDATE_MTIME → 跳过，更新指纹 |
| size 也变了 | 重新下载了不同版本 | REPROCESS → 创建新任务 |

#### 场景C：源文件删除

```
之前：/source/movie.mkv  → 已入库 SUCCESS
现在：/source/movie.mkv  → 文件不存在
```

**现有行为**：扫描时文件不存在 → 不创建任务 → 历史记录保留 ✅

**无需特殊处理**。建议：
- 前端展示"源文件已不存在"的状态提示（`file_location=source` 但文件不存在）

#### 场景D：同名新文件（不同内容）

```
之前：/source/movie.mkv  size=1.5GB  fingerprint=abc123  → 已入库 SUCCESS
现在：/source/movie.mkv  size=8.2GB  fingerprint=xyz789  → 删了旧的，下了4K版
```

**检测**：L1 路径匹配命中 → 指纹不同 → size 变了 → REPROCESS

**关联旧任务**：无需显式关联，入库去重机制自动处理

**是否重新入库是合理方式？**

是的，因为：
1. 文件内容确实不同（size变了），需要重新刮削确认信息
2. 入库去重阶段会通过 `provider_id` 匹配到同一影视，按去重策略处理旧版本
3. 旧版本文件按策略（replace/quality）移入回收站，不会丢失
4. 回收站 .meta 文件记录了 task_id 和 reason，可追溯

**REPROCESS 完整流程**：
1. 创建新任务，正常走刮削 → 入库流程
2. 入库去重阶段：`provider_id` 匹配到同一影视 → 按去重策略处理
3. 旧版本文件按策略移入回收站
4. 旧任务 `file_location` 更新为 `recycle`

#### 场景E：BT 做种目录（只读场景）

见 4.3 源目录三级策略

#### 场景F：源目录垃圾文件清理

见 4.3 源目录三级策略

### 4.3 源目录三级策略（互斥）

源目录的文件处理策略分为三级，**互斥选择**，从保守到激进：

```
┌─────────────────────────────────────────────────────────────────┐
│  级别1: 只读保护         级别2: 智能清理         级别3: 完全清理  │
│  (read_only)            (smart_cleanup)        (full_cleanup)   │
│                                                                 │
│  ←── 最保守                                    最激进 ──→       │
│                                                                 │
│  不删任何文件           AI识别+用户确认         删除所有非媒体    │
│  不移任何文件           白名单/黑名单           删除源视频+附属   │
│  只复制到中转           清理广告/样品           清理空目录        │
└─────────────────────────────────────────────────────────────────┘
```

#### 配置设计

```yaml
source_policy:
  # 源目录清理策略（三选一，互斥）
  cleanup_mode: "smart_cleanup"     # "read_only" / "smart_cleanup" / "full_cleanup"
                                     #
                                     # read_only    - 只读保护：只复制，不删/不移/不改源目录任何文件
                                     #                适用：BT做种目录
                                     #
                                     # smart_cleanup - 智能清理：AI识别垃圾文件+用户确认，保护有用文件
                                     #                 适用：大多数场景（推荐）
                                     #
                                     # full_cleanup  - 完全清理：入库后删除源文件+附属，清理非媒体文件
                                     #                 适用：纯下载临时目录

  # 入库后源文件处理（仅 full_cleanup 模式生效）
  delete_source_after_import: true   # true=移入回收站 / false=保留

  # 智能清理配置（仅 smart_cleanup 模式生效）
  smart_cleanup:
    ai_enabled: true                 # 是否启用AI辅助判断
    protect_extensions:              # 受保护扩展名（永远不清理）
    - ".nfo"
    - ".info"
    - ".torrent"
    - ".jpg"
    - ".png"
    - ".webp"
    whitelist_patterns:              # 白名单（明确保留的文件模式）
    - "*.srt"
    - "*.ass"
    - "*/Subs/*"
    blacklist_patterns:              # 黑名单（明确清理的文件模式，无需AI判断）
    - "RARBG*"
    - "*.url"
    - "*/Sample/*"
    - "*/sample/*"
    cleanup_empty_dirs: true         # 清理后删除空目录
    confirm_before_cleanup: true     # AI判断结果是否需要用户确认
```

#### 三级策略对比

| 操作 | read_only | smart_cleanup | full_cleanup |
|------|-----------|---------------|--------------|
| 复制视频到中转 | ✅ | ✅ | ✅ |
| 入库后删除源视频 | ❌ | ❌ | 按 delete_source_after_import |
| 清理广告/垃圾文件 | ❌ | ✅ AI+确认 | ✅ 自动 |
| 清理非媒体文件 | ❌ | ✅ AI+确认 | ✅ 全部 |
| 清理空目录 | ❌ | ✅ | ✅ |
| 保护 .nfo/.torrent 等 | ✅ 自动 | ✅ protect_extensions | ❌ 全删 |

#### AI 辅助清理流程

```
扫描源目录 → 构建目录树
  → 黑名单匹配 → 直接标记清理（无需AI）
  → 白名单匹配 → 直接标记保留（无需AI）
  → protect_extensions → 直接标记保留
  → 剩余未知文件 → 提交AI判断
    → AI返回建议（保留/清理+理由）
  → 合并结果 → 展示给用户确认
  → 用户确认后执行清理（移入回收站）
```

**AI 提示词设计**：

```
以下是源目录的文件树，请判断哪些文件是垃圾文件（广告、样品、无用信息）需要清理。
已知保留的文件：视频文件(.mkv/.mp4/...)、字幕文件(.srt/.ass/...)、
  影视信息(.nfo/.info)、海报图片(.jpg/.png)、种子文件(.torrent)

目录树：
{directory_tree}

请对每个非保留文件给出判断：
- 保留：说明原因（如：可能是字幕相关、可能是影视元数据）
- 清理：说明原因（如：广告文件、样品视频、无用文本）
```

**实现**：

```python
def smart_cleanup_source(source_dir, config, llm_scraper=None):
    blacklist = config.get("blacklist_patterns", [])
    whitelist = config.get("whitelist_patterns", [])
    protect_exts = set(config.get("protect_extensions", []))

    file_tree = build_file_tree(source_dir)
    decisions = {}

    for f in file_tree["all_files"]:
        ext = os.path.splitext(f)[1].lower()
        if ext in ALLOWED_MEDIA_EXTS or ext in protect_exts:
            decisions[f] = {"action": "keep", "reason": "媒体/受保护文件"}
            continue
        if match_patterns(f, blacklist):
            decisions[f] = {"action": "cleanup", "reason": "匹配黑名单"}
            continue
        if match_patterns(f, whitelist):
            decisions[f] = {"action": "keep", "reason": "匹配白名单"}
            continue
        decisions[f] = {"action": "pending", "reason": "待AI判断"}

    if config.get("ai_enabled") and llm_scraper:
        pending = [f for f, d in decisions.items() if d["action"] == "pending"]
        if pending:
            ai_decisions = llm_scraper.judge_junk_files(pending, source_dir)
            decisions.update(ai_decisions)

    if config.get("confirm_before_cleanup"):
        return {"status": "needs_confirm", "decisions": decisions}

    execute_cleanup(decisions, recycle_dir)
```

### 4.4 场景决策矩阵

| 场景 | 检测方式 | action | 处理 |
|------|---------|--------|------|
| 新文件 | L1路径无历史 + L2指纹无历史 | CREATE | 正常创建任务，写入指纹 |
| 已处理，无变化 | L1路径匹配 + 指纹相同 | SKIP | 更新 last_seen_at |
| 已处理，仅mtime变 | L1路径匹配 + 指纹不同 + size不变 | UPDATE_MTIME | 更新指纹+mtime，跳过 |
| 已处理，大小变了 | L1路径匹配 + 指纹不同 + size变 | REPROCESS | 创建新任务，去重处理旧版本 |
| 文件改名 | L1路径无历史 + L2指纹匹配 | RENAME_DETECTED | 更新路径引用，跳过 |
| 正在处理中 | L1路径匹配 + PROCESSING | SKIP | 跳过 |
| 待确认中 | L1路径匹配 + CONFIRMING | SKIP | 跳过 |
| 源文件删除 | 扫描不到文件 | — | 不创建任务，保留历史 |

### 4.5 回收站目录结构（区分来源）

回收站中的文件来源于两个方向，用户需要能一眼区分：

```
{recycle_dir}/
├── 2026-05-28/
│   ├── [源目录]/                          ← 来自源目录的文件
│   │   ├── movie.mkv                      # 入库后清理的源文件
│   │   ├── movie.mkv.meta
│   │   ├── RARBG.mp4                      # 垃圾清理的广告文件
│   │   └── RARBG.mp4.meta
│   └── [入库目录]/                        ← 来自入库目录的文件
│       └── 影视/
│           └── 电影/
│               └── 2010/
│                   ├── Inception.2010.1080p.mkv    # 被替换的旧版本
│                   └── Inception.2010.1080p.mkv.meta
└── 2026-05-29/
    └── ...
```

**目录规则**：

| 文件来源 | 回收站子目录 | 示例 |
|---------|------------|------|
| 源目录清理 | `[源目录]/{相对路径}` | `[源目录]/downloads/movie.mkv` |
| 源目录垃圾清理 | `[源目录]/{相对路径}` | `[源目录]/downloads/RARBG.mp4` |
| 入库目录替换 | `[入库目录]/{相对路径}` | `[入库目录]/影视/电影/2010/Inception.mkv` |

**实现**：

```python
def _recycle_subpath(original_path: str, source_dir: str, import_roots: list) -> str:
    """根据文件原始路径确定回收站子目录"""
    abs_path = os.path.abspath(original_path)
    source_abs = os.path.abspath(source_dir)

    if abs_path.startswith(source_abs + os.sep):
        rel = os.path.relpath(abs_path, source_abs)
        return os.path.join("[源目录]", rel)

    for root in import_roots:
        root_abs = os.path.abspath(root)
        if abs_path.startswith(root_abs + os.sep):
            rel = os.path.relpath(abs_path, root_abs)
            return os.path.join("[入库目录]", rel)

    return os.path.join("[其他]", os.path.basename(abs_path))
```

**.meta 文件增加来源标记**：

```json

  "reason": "quality_replace",
  "task_id": "def456",
  "moved_at": "2026-05-28T14:30:00",
  "file_size_mb": 1500.0,
  "source_title": "盗梦空间",
  "provider_type": "tmdb",
  "provider_id": "27205"

```

`source_zone` 取值：

- `import` — 来自入库目录

## 六、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 回收站磁盘空间 | 大量文件移入回收站可能占满磁盘 | 1. .meta 文件记录来源便于清理 2. 文档建议定期清理 3. 可选：增加回收站容量监控 |
| 跨设备回收站移动 | 源文件和回收站可能不在同一分区 | `move_to_recycle()` 内部处理跨设备（copy+delete） |
| 向后兼容 | 旧配置 `quarantine_dir` | `config_loader.py` 自动迁移旧配置到 `recycle_dir` |
| 数据库迁移 | 已有数据的 `file_location='quarantine'` | `_migrate_schema()` 批量 UPDATE |
| 临时文件回收 | 中转临时文件是否也需要移入回收站 | 临时文件（.tmp）直接删除不进回收站，因为回收站主要用于有价值的影视文件 |
| 性能 | 大文件 move_to_recycle 比直接删除慢 | 回收站操作是文件移动（同分区瞬间完成），只有跨分区才需复制 |
| 文件指纹误判 | 不同文件恰好大小相同 | 指纹匹配仅作为辅助参考，不作为唯一判断依据；最终由 Provider ID 确认 |
| BT 做种误删 | read_only_mode 未开启时可能删除做种文件 | 默认 read_only_mode=false 保持现有行为；文档强调做种场景必须开启 |
| 垃圾清理误删 | glob 模式可能误匹配有用文件 | 垃圾清理默认 disabled；清理时移入回收站而非直接删除，可恢复 |
