# rclone 来源永久删除与失败恢复

修复 fnOS 0.3.24 在 rclone/FUSE 云盘来源上只完成隔离重命名、未完成真实删除的问题，并让既有删除账本可安全续做。

## 问题陈述

真机 `/vol02/.../fnos_movie` 是 `fuse.rclone`。程序已把《通天塔》来源目录认领为 `.nas-media-delete-68e175...deleting`，但其中约 25.96 GB 主视频和附带文件全部仍在；活动账本未归档，任务为入库成功但来源处置 `BLOCKED`。代码在重命名前后比较 `st_dev + st_ino`，隐含“inode 随 rename 稳定”的本地文件系统假设；rclone 使用虚拟 inode，导致实际 unlink 前失败。恢复返回 `BLOCKED` 后又继续检查已被认领的旧路径，使真实错误被“源单元目录不存在”覆盖。

## 目标结果

- 本地文件系统继续使用 inode + device 的强身份门禁。
- 已识别远程/FUSE 来源使用可跨 rename 的受限身份：挂载身份、任务账本、隔离区路径、成员类型/相对名称/大小/mtime；额外文件、符号链接、特殊文件或越界仍停止删除。
- 远程隔离区只允许在验证后的 `.nas-media-delete-<unit>.deleting` 内按完整路径删除；不对原始业务路径或片库执行递归删除。
- 旧 0.3.24 活动账本无需移动或重拷影片即可恢复完成。
- 任意恢复失败立即停止并把真实原因写入来源单元、任务详情和日志，不再被“路径不存在”覆盖。

## 范围与非目标

范围：`permanent_delete.py`、来源单元协调器、永久删除专项测试、安全/存储/来源文档、需求与验收记录。

非目标：不远程操作用户当前 fnOS 隔离区；不自动清理历史 `.write_test_*`；不放宽目标片库禁删；不把云盘删除改成本地回收复制。

## 推荐方案

1. 删除账本记录身份模式和当前挂载的稳定事实；旧账本按当前挂载类型安全推导，未知挂载失败关闭。
2. 快照比较分为 `inode` 与 `remote_snapshot`：后者忽略不稳定 inode，但仍验证当前同一挂载、完整相对树、文件大小/mtime、无额外成员、无链接和特殊文件。
3. 本地隔离区保留 dir-fd 删除；远程隔离区使用逐层边界复核的路径删除，所有副作用仍只能发生在已验证隔离区。
4. 恢复入口对所有非成功结果立即返回；错误消息包含原始验证或删除失败原因。
5. 维护循环继续使用账本重试；完成后写 `DONE` 并归档账本。

## 验收标准

- 模拟 rclone rename 后全部成员 inode 改变，永久删除仍成功且隔离区消失。
- 相同场景在删除阶段中断，重启后只按已知账本续做并成功归档。
- 隔离区出现未知文件、链接、特殊文件或挂载身份不一致时零误删并显示具体原因。
- 本地文件系统 inode 发生异常变化时仍阻断。
- 目标片库哨兵文件在全部场景中哈希不变。
- 既有 fnOS 账本格式可恢复，不要求用户手动移动 `.deleting`。

## 决策理由

不直接移除 inode 检查：这会降低本地来源的安全性。按挂载能力选择身份证据，既保留本地强门禁，也承认远程虚拟文件系统不保证 POSIX inode 语义。远程路径删除只作为隔离区内部实现，不是对原来源开放 `rmtree`。

## 约束与风险

- 删除不可恢复，任何证据不完整都必须停在隔离区。
- 远程 mtime 也可能被 Provider 改写；当前只接受 rename 后成员事实保持一致的挂载，异常进入人工诊断，不猜测。
- WebDAV/rclone 可能不支持 dir-fd 操作，因此远程分支必须有独立测试，不能只用 tmp_path 证明。
- 旧账本没有挂载字段；只允许在当前配置仍识别为远程且来源根、任务隔离区、账本成员全部匹配时兼容恢复。

## 拒绝标准

- 通过跳过所有身份验证来“修好”云盘删除。
- 对来源根、原电影路径或目标片库调用通用递归删除。
- 失败后仍把任务显示成来源处理成功，或只显示“路径不存在”。
- 只跑本地正常文件系统 happy path。
