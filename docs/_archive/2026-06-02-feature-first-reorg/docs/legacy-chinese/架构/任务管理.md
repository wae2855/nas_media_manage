# 任务管理模块技术文档

> 对应源码路径：
> - `media_importer/core/task_manager.py` — 任务管理器主类
> - `media_importer/core/db/connection.py` — 数据库初始化与 Schema 迁移
> - `media_importer/core/db/constants.py` — 常量定义（状态、DDL、默认维度）
> - `media_importer/core/db/task_repo.py` — 任务 CRUD 数据访问层
> - `media_importer/core/db/subtitle_repo.py` — 字幕 CRUD 数据访问层
> - `media_importer/core/db/dimension_repo.py` — 维度 CRUD 数据访问层
> - `media_importer/pipeline/runner.py` — 流水线运行器
> - `media_importer/pipeline/steps.py` — 流水线步骤实现
> - `media_importer/pipeline/confirm.py` — 确认/重新分类逻辑

## 1. 概述

任务管理模块是 影音库AI智能整理的核心调度中心，负责视频文件从扫描发现到最终入库的全生命周期管理。模块采用三层架构：

| 层级 | 组件 | 职责 |
|------|------|------|
| 业务层 | `TaskManager` | 任务创建、状态流转、源端去重、回收区管理 |
| 数据层 | `task_repo` / `subtitle_repo` / `dimension_repo` | SQLite CRUD 操作，JSON 字段序列化 |
| 基础设施层 | `connection` / `constants` | 数据库连接、Schema 迁移、常量定义 |

`TaskManager` 通过组合 `task_repo` 和 `subtitle_repo` 的函数实现业务逻辑，自身不直接执行 SQL。所有数据库写操作通过 `threading.RLock`（`_sqlite_conn_lock`）保证线程安全。

## 3. 任务状态机

### 3.1 有效状态

```
VALID_STATUSES = ["PENDING", "PROCESSING", "SUCCESS", "FAILED", "SKIPPED", "CONFIRMING"]
```

> 历史状态 `NEEDS_REVIEW`、`ROLLBACK`、`DUPLICATE_REVIEW` 在 Schema 迁移中已合并为 `FAILED` 或 `SKIPPED`。

### 3.2 业务状态映射

系统对外呈现 4 个业务状态，技术状态作为内部子状态保留：

| 业务状态 | 技术状态 | 含义 | 前端展示 |
|---------|---------|------|---------|
| 待处理 | PENDING | 等待流水线拾取 | "待处理" |
| 处理中 | PROCESSING | 流水线正在执行 | "处理中" |
| 处理中 | CONFIRMING（子状态） | 等待用户确认后继续 | "处理中 · 需确认" |
| 失败 | FAILED | 流程中断，源文件保留在源目录等用户决策 | "失败" |
| 完成 | SUCCESS | 成功入库 | "完成" |
| 完成 | SKIPPED（子状态） | 跳过/忽略不入库 | "完成 · 跳过" |

> DB 和 API 中仍使用技术状态值（PENDING/PROCESSING/CONFIRMING/FAILED/SUCCESS/SKIPPED），前端通过映射表转换为业务状态展示。

### 3.4 状态流转规则

| 当前状态 | 触发条件 | 目标状态 | 说明 |
|----------|----------|----------|------|
| - | 创建任务 | PENDING | 初始状态 |
| PENDING | process_one 开始 | PROCESSING | 开始处理 |
| PROCESSING | 流水线全部完成 | SUCCESS | 入库成功 |
| PROCESSING | PipelineError 异常 | FAILED | 处理失败 |
| PROCESSING | PipelineSkipError 异常 | SKIPPED | 跳过（同名/质量优先保留） |
| PROCESSING | _needs_confirm 标记 | CONFIRMING | 置信度不足，需人工确认 |
| PROCESSING | manual_review 启用 | CONFIRMING | 人工检查模式 |
| CONFIRMING | confirm_task | SUCCESS | 确认入库 |
| CONFIRMING | reclassify_task | PROCESSING → SUCCESS/FAILED/SKIPPED | 重新分类后继续 |
| FAILED | retry_task | PENDING | 重试（retry_count +1） |
| SKIPPED | retry_task | PENDING | 重试（retry_count +1） |

### 3.5 Schema 迁移中的状态合并

在 `_migrate_schema` 中，历史状态被自动合并：

| 旧状态 | 新状态 | 原因 |
|--------|--------|------|
| NEEDS_REVIEW | FAILED | 简化状态机，审核需求通过 CONFIRMING 处理 |
| ROLLBACK | FAILED | 回退视为失败，可重试 |
| DUPLICATE_REVIEW | SKIPPED | 重复审核跳过 |

## 4. 任务生命周期

### 4.1 流水线步骤

```
PIPELINE_STEPS = scan → copy → scrape → validate → classify → dedup → rename → import → notify → record
```

| 步骤编号 | 步骤名 | 进度区间 | 说明 |
|----------|--------|----------|------|
| 1 | scan | 0-20 | 扫描源目录，创建任务 |
| 2 | copy | 20-30 | 复制文件到中转目录 |
| 3 | scrape | 35-50 | AI + TMDB 刮削元数据 |
| 4 | validate | 52-55 | 验证刮削结果完整性 |
| 5 | classify | 56-60 | 按维度匹配入库路径规则 |
| 6 | dedup | 65-70 | 入库同名检测 |
| 7 | rename | 72-75 | 按模板生成最终文件名 |
| 8 | import | 80-90 | 移动文件到目标目录，清理源文件 |
| 9 | notify | 95 | 发送通知 |
| 10 | record | 100 | 记录最终状态 |

### 4.2 完整生命周期流程

```
┌─────────────┐
│  文件监控/    │
│  手动触发扫描  │
└──────┬──────┘
       │
       ▼
┌──────────────────┐     dedup_enabled=true
│  scan_and_filter  │──────────────────────┐
│  (源端去重过滤)    │                      │
└──────┬───────────┘                      │
       │ dedup_enabled=false               │
       ▼                                  ▼
┌──────────────────┐              ┌───────────────┐
│  scan_and_group   │              │  去重判断       │
│  (直接扫描分组)    │              │  check_source_ │
└──────┬───────────┘              │  duplicate     │
       │                          └───────┬───────┘
       │                                  │
       │              ┌───────────────────┤
       │              │ SKIP              │ CREATE
       │              ▼                   ▼
       │        ┌──────────┐      ┌──────────────┐
       │        │ 跳过(正在  │      │ create_task   │
       │        │ 处理/确认) │      │ (PENDING)     │
       │        └──────────┘      └──────┬────────┘
       │                                 │
       └─────────────┬───────────────────┘
                     │
                     ▼
              ┌─────────────┐
              │  process_one │
              │  (PENDING →  │
              │  PROCESSING) │
              └──────┬──────┘
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   ┌─────────┐ ┌──────────┐ ┌──────────┐
   │ SUCCESS │ │  FAILED  │ │ SKIPPED  │
   │ (入库)  │ │(源文件保留)│ │(源文件按配置)│
   └─────────┘ └────┬─────┘ └──────────┘
                     │
                     │ retry_task
                     ▼
              ┌───────────┐
              │  PENDING   │
              │ (重试)     │
              └───────────┘
```

### 4.3 确认流程（CONFIRMING）

当任务进入 CONFIRMING 状态后，有两种后续操作：

**确认入库（confirm_task）**：
```
CONFIRMING → confirm_task()
  → _step_import_from_confirm()
    → dedup → rename → import → notify → record
  → SUCCESS
```

**重新分类（reclassify_task）**：
```
CONFIRMING → reclassify_task(new_dimensions)
  → 更新 scrape_dimensions
  → classify → dedup → rename → import → notify → record
  → SUCCESS / FAILED / SKIPPED
```

### 4.4 源端去重检测

`TaskManager.check_source_duplicate()` 在扫描阶段判断源文件是否已有历史任务：

| 历史状态 | 动作 | 原因 |
|----------|------|------|
| 无记录 | CREATE | 新文件 |
| PROCESSING / CONFIRMING | SKIP | 任务正在处理中，避免重复 |
| 其他（SUCCESS/FAILED/SKIPPED） | CREATE | 历史任务已结束，允许重新创建 |

## 5. 目录系统（file_location）

### 5.1 file_location 值定义

| 值 | 含义 | 文件实际位置 |
|----|------|-------------|
| `source` | 源目录 | `source_dir` 下的原始路径 |
| `temp` | 中转目录 | `temp_dir` 下的临时副本 |
| `import` | 已入库 | `path_rules` 匹配的目标路径 |
| `recycle` | 回收站 | `recycle_dir` 下的回收站路径 |
| `deleted` | 已删除 | 文件已从源目录清理 |

### 5.2 file_location 流转

```
  source ──── copy步骤 ────→ temp ──── import步骤 ────→ import
    │                          │
    │                          │ 失败/跳过
    │                          ▼
    │                      (清理temp，直接rm删除)
    │
    │ 完成状态(SUCCESS/SKIPPED) + cleanup_source_after_done=true
    └──── move_to_recycle_with_companions ──→ recycle

  source ──── 完成状态 + cleanup_source_after_done=false ────→ source (保留)

  source ──── FAILED ────→ source (保留，等用户决策)
```

### 5.3 file_location 与状态的对应关系

| file_location | 典型状态 | 业务状态 | 说明 |
|---------------|----------|---------|------|
| source | PENDING | 待处理 | 任务刚创建，文件在源目录 |
| source | FAILED | 失败 | 处理失败，源文件保留在源目录等用户决策 |
| temp | PROCESSING / CONFIRMING | 处理中 | 文件已复制到中转目录 |
| import | SUCCESS | 完成 | 文件已入库到目标目录 |
| recycle | SKIPPED | 完成(跳过) | 忽略任务时源文件移入回收站 |
| deleted | SUCCESS | 完成 | cleanup_source_after_done=true 且无回收站时源文件已删除 |

> **关键变更**：FAILED 状态下源文件保留在源目录（file_location=source），不再自动移入回收站。仅完成状态（SUCCESS/SKIPPED）才按 cleanup_source_after_done 配置处理源文件。

### 5.4 Schema 迁移中的 file_location 修正

首次添加 `file_location` 列时，系统自动修正历史数据：

```sql
UPDATE tasks SET file_location='import'    WHERE status='SUCCESS' AND import_success=1;
UPDATE tasks SET file_location='deleted'   WHERE status='SKIPPED';
UPDATE tasks SET file_location='recycle' WHERE status='NEEDS_REVIEW';
UPDATE tasks SET file_location='temp'      WHERE status='CONFIRMING';
```

后续迁移还会修正 `file_location='source'` 但状态已终态的记录。

### 5.5 回收站管理

`TaskManager.move_to_recycle_bin()` 负责将文件移入回收站：

1. 创建回收站目录（如不存在）
2. 检查文件是否已在回收站内（避免重复移动）
3. 移动视频文件（同名冲突时自动添加编号后缀 `_1`, `_2` ...）
4. 移动关联字幕文件
5. 更新字幕记录的 `target_path`
6. 更新任务的 `source_path`、`file_location`、`error_message`
7. 清理源目录中的空父目录（受保护目录除外）

受保护目录（不会被清理空目录）：`source_dir`、`temp_dir`、`recycle_dir`

## 7. 职责边界

### 负责

- 任务全生命周期管理（创建、状态流转、进度更新）
- 源端去重检测（路径匹配 + 指纹匹配，六大场景决策）
- 回收站文件移入（move_to_recycle_bin）
- 任务数据持久化（CRUD 操作委托 task_repo）
- 字幕关联管理

### 不负责

- 文件 I/O 操作（复制/移动/删除由 storage 模块执行）
- 刮削逻辑（由 scraper 模块执行）
- 流水线编排（由 pipeline 模块执行）
- 配置管理（由 config_loader 执行）
- 通知发送（由 notify 模块执行）

### 8.1 交互关系图

```
┌──────────────┐     创建/查询任务      ┌──────────────┐
│   Pipeline   │──────────────────────→│  TaskManager  │
│   Runner     │←──────────────────────│              │
│              │     更新进度/状态       │              │
└──────┬───────┘                       └──────┬───────┘
       │                                      │
       │ 调用步骤方法                           │ 调用 repo 函数
       │                                      │
       ▼                                      ▼
┌──────────────┐                       ┌──────────────┐
│  StepsMixin  │                       │   task_repo   │
│  ConfirmMixin│                       │ subtitle_repo │
└──────┬───────┘                       │ dimension_repo│
       │                               └──────┬───────┘
       │ 调用存储/刮削/通知模块                  │
       │                                      │ SQL 操作
       ▼                                      ▼
┌──────────────────────────────┐      ┌──────────────┐
│ FileCopier  FileScanner      │      │   SQLite DB   │
│ MetadataScraper  Classifier  │      │  (tasks.db)   │
│ DedupChecker  FileMover     │      └──────────────┘
│ HookRunner  HermesNotifier  │
└──────────────────────────────┘
```

### 7.2 模块交互详情

| 调用方 | 被调用方 | 交互方式 | 说明 |
|--------|----------|----------|------|
| PipelineRunner | TaskManager | 方法调用 | 创建任务、获取待处理任务、更新进度 |
| PipelineRunner | task_repo | 直接调用 | 绕过 TaskManager 更新特定字段（如 file_location、import_video_path） |
| StepsMixin | task_repo | 直接调用 | 更新字幕 target_path、import_path |
| ConfirmMixin | task_repo | 直接调用 | 确认/重新分类时更新任务状态 |
| TaskManager | task_repo | 函数调用 | CRUD 操作委托 |
| TaskManager | subtitle_repo | 函数调用 | 字幕创建/查询/更新 |
| TaskManager | dimension_repo | 间接（通过 conn） | 回收站操作中查询字幕 |
| FileScanner | TaskManager | 方法调用 | `check_source_duplicate()` 源端去重 |
| API Handler | TaskManager | 方法调用 | 任务列表、详情、统计、重试等 |

### 7.3 TaskManager 公共 API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `create_task` | video_path, video_file, subtitle_files, file_size_mb, initial_status | dict | 创建任务（含字幕） |
| `get_task` | task_id | dict | 获取任务详情（含字幕虚拟字段） |
| `get_next_pending` | - | dict / None | 获取下一个待处理任务（按创建时间升序） |
| `update_task` | task (dict) | - | 更新任务字段（排除虚拟字段） |
| `update_progress` | task, step_num, step_name, percentage, **kwargs | - | 更新进度（同步更新内存和数据库） |
| `list_tasks` | status, limit, offset, exclude_completed | list | 分页查询任务 |
| `list_all_tasks` | limit, offset | list | 查询全部任务 |
| `retry_task` | task_id | dict / None | 重试失败/跳过的任务 |
| `retry_all_failed` | - | list | 批量重试所有失败/跳过任务 |
| `clear_tasks` | status | - | 清除任务（可按状态筛选） |
| `count_by_status` | - | dict | 按状态统计任务数 |
| `has_running_tasks` | - | bool | 是否有正在处理的任务 |
| `check_source_duplicate` | source_path | dict | 检查源文件是否已有历史任务 |
| `move_to_recycle_bin` | task_id, source_path, subtitle_paths, recycle_dir | - | 将文件移入回收站 |

### 8.4 线程安全设计

- `TaskManager.__init__` 中创建 `threading.RLock`（`self._lock`），但实际数据库写锁由 `connection._sqlite_conn_lock`（模块级 RLock）统一管理
- 所有 `task_repo` 和 `subtitle_repo` 的写操作都包裹在 `with _sqlite_conn_lock:` 中
- `conn = sqlite3.connect(db_path, check_same_thread=False)` 允许跨线程使用同一连接，配合 RLock 保证安全
- SQLite WAL 模式允许读写并发，进一步提升性能
