# 来源永久删除闭环与 fnOS 发版版本治理

## 问题

真机 `0.3.23` 已完成影片入库，但来源处置停在 `WAITING`，且 rclone FUSE 来源残留 `.write_test_*`。证据显示旧包未冻结广告小视频判定、待处理来源单元只在新建任务路径重试，写权限探针又可能在重复关闭文件描述符时抛错并终止 watcher。

发布侧已有根 `VERSION` 和包内一致性规范，却只校验“同一个包内版本一致”，没有持久记录上一次候选包或 fnOS 验收版本，也没有禁止“同版本、不同源码”再次出包。根 `VERSION` 尚未纳入版本控制，使规范仍依赖人工记忆。

## 目标

- 新任务完成后，即使没有新文件进入，也会在既有来源轮询中重试待处理来源单元。
- FUSE 文件系统关闭行为异常时，权限检查不得使 watcher 线程退出；仅清理能用随机令牌证明属于本次检查的探针。
- 物理快照未变化的旧来源单元可补齐当前冻结的媒体候选证据；任何变化、未知成员或任务未完成仍失败关闭。
- 每个新的 fnOS 候选包版本必须高于历史候选；同版本只允许源码指纹一致的确定性重建。
- 仓库可查询“当前开发版本、最近候选包、最近 fnOS 验收正常版本”，本地构建与真机验收明确分开。

## 方案概述

1. `FileWatcher` 在完成来源扫描后调用轻量维护回调；回调只查询待处理来源单元，存在待处理项时才进入来源处置，不扫描目标片库。
2. 来源单元重试对物理快照完全一致且缺少候选证据的记录执行一次有边界的证据补齐；沿用现有永久删除隔离区、账本和片库保护门禁。
3. 写权限探针使用随机文件名和随机内容令牌，关闭及清理均容错；删除前重新以 `O_NOFOLLOW` 打开并核对单链接普通文件及令牌，不对历史未知探针做通配删除。
4. 新增受版本控制的发布台账和单一版本工具。构建前比较 SemVer 与源码指纹，构建成功后记录候选包 SHA-256；真机验收后用显式命令标记正常版本。
5. 当前代码进入下一个候选版本 `0.3.24`；测试不再把具体版本号硬编码为常量。

## 影响面

- 代码：filesystem、source_files、monitor、runtime_service、deploy 构建链。
- 数据：只补齐物理快照未变化的来源单元判定；不移动或删除目标片库内容。
- 文档：发布工作流、fnOS 部署、监控、来源文件和安全标准。
- 测试：FUSE 故障注入、维护重试、来源证据补齐、版本单调门禁及候选/验收台账。

## 备选方案

- 只提醒人工修改版本：已被现状证明会遗漏。
- 仅依赖 Git tag：本项目常在真机验收前生成未提交候选包，无法覆盖候选包事实。
- 每次轮询执行完整 pipeline：会额外读取目标片库，不符合硬盘休眠友好边界。
- 自动清理所有 `.write_test_*`：无法证明历史文件身份，存在误删风险。
