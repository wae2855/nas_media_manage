# 电视剧手动绑定继承与批量继续处理计划

把一次明确的电视剧 Provider 选择安全地传播到同目录同剧分集，并让可安全处理的任务进入受限并发队列，同时补齐长请求的可见进度和部分失败反馈。

## Problem Statement

fnOS 0.3.28 的《北海鲸梦》实操暴露了三段断裂：批量应用期间没有忙碌反馈；应用完成后任务仍停在待确认；同剧发现只扫描 `PENDING/AWAIT_REVIEW`，因此正在处理或尚未刮削的分集无法继承人工选择。用户看到“应用其他剧集”时合理期待一次选择可覆盖整剧，但现有实现只更新当时已进入待确认的子集。

## Target End State

- 批量操作从点击到完成始终显示明确的忙碌状态，并锁定会造成重复提交的交互。
- 同目录、同标准化剧名且季集号有效唯一的排队分集可持久继承人工选定的 Provider 作品身份；每集仍保留自己的季集号。
- 已待确认且不存在冲突或兜底风险的分集可批量提交确认，并受现有 `max_concurrent=1..2` 统一限制。
- 处理中任务不被中途改写；结果明确区分立即应用、排队继承、处理中暂不变更、冲突/失败。
- 服务重启后不会把继承意图丢失，也不会因恢复而自动覆盖或重复入库。

## Scope and Non-Goals

范围包含任务业务服务、SQLite 持久字段及迁移、导入流水线的作品绑定消费、API 响应、任务前端弹窗、状态文案、测试和事实文档。不改变 Provider 匹配阈值，不降低目录/季集号/冲突安全门禁，不在运行中的任务中途替换元数据，不增加并发上限，不改变文件覆盖、删除、回收和来源清理规则。

## Proposed Solution

1. 在任务表持久化“人工 Provider 绑定待消费”字段，并以同一实际父目录、标准化剧名和有效唯一季集号计算安全同剧集合。
2. 待确认任务与排队任务都写入待消费绑定并进入或保持真实 `QUEUED`，不伪造已刮削结果。任务取得并发槽后在刮削步骤优先消费绑定，按指定 Provider ID 获取详情并保留文件自身季集号，避免候选搜索覆盖。
3. 正在处理的任务只在响应中列为暂不变更；不做竞态写入。若后续进入待确认，用户界面如实提示仍需处理。
4. 已待确认任务通过专用状态转换重新排队；流水线重算分类和冲突，安全任务继续入库，冲突/兜底重新回到待确认。这样复用持久任务队列、重启恢复与统一并发槽，不依赖进程内确认线程。
5. 前端在预览和提交阶段分别展示转动图标、阶段文案与禁用态，完成后展示分类汇总，不用单一成功 Toast 隐藏跳过或失败。

## Representative Proof Slice

构造《北海鲸梦》E01=`AWAIT_REVIEW`、E04=`RUNNING`、E05=`QUEUED`：E01 选择 TMDB 86941 后，E01 以人工绑定重新排队，E04 不被改写，E05 持久记录绑定；E05 开始处理时直接使用 86941 且保留 S01E05。该切片通过后才扩展 UI 和完整批量回归。

- 所有文件操作继续走既有确认、文件包和回收安全路径；本变更不新增直接删除或覆盖。
- 全量测试无本次新增失败，专项 UI 在真实 Chromium 通过；自我评审结论为 APPROVE 或所有阻断项已修复后再 APPROVE。

## Decision Rationale

直接给 `QUEUED` 任务写完整刮削结果会在普通 runner 启动时被重新刮削覆盖；把它直接改成 `RUNNING` 又会虚报并发并破坏领取语义。因此持久化“小而明确的人工身份意图”，并在任务真正取得槽位后消费，是兼顾用户预期、重启恢复和现有状态机的最小安全方案。处理中任务不做中途修改，是为了避免同时写入刮削、分类和冲突预览造成竞态。

## Constraints and Boundaries

- `features/tasks/` 负责同剧集合与批量动作事实，API handler 不承载业务策略。
- `features/import_flow/` 只在取得任务槽后消费绑定；Provider ID 是作品身份，季集号始终来自具体文件任务。
- 绑定范围必须重新由服务端计算，不能信任前端提交的任意任务 ID。
- 任何目标片库冲突、兜底规则或文件处置仍要求现有显式确认。
- 前端使用现有原生 JS/CSS 和 `.spinner`，不引入依赖或第七个 CSS 文件。

## Risk Analysis

- 绑定字段重启后重复消费：使用明确消费状态和 CAS/任务领取边界，成功后清理；失败不得静默转普通搜索。
- 自动确认扩大文件操作：仅对已完整重算且无冲突/兜底的 `AWAIT_REVIEW` 任务调用既有确认入口，保留逐项失败结果。
- 同目录包含不同版本或重名作品：继续要求标准化标题相交、季集号唯一，并排除不同人工 Provider；不按目录全量广播。
- 处理中任务后来仍需人工确认：响应和 UI 明示“处理中未改写”，不承诺已覆盖。
- UI 关闭或网络中断：后端动作幂等，前端重新加载后以任务事实为准，不用本地动画冒充后台成功。

## Rejection Criteria

- 为实现继承而提前把排队任务标记成 `RUNNING`，或绕过最大并发限制。
- 对正在处理任务直接改写刮削结果。
- 将不同目录、重复季集号、不同人工 Provider 或未决冲突任务自动传播/入库。
- 只增加 spinner 而不解决状态、继承和部分失败真实性。
- 测试通过但前端仍把“仅待确认子集”表述成“全部剧集”。
