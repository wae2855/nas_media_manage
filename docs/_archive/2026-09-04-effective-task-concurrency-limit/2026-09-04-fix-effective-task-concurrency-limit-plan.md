# 任务并发配置真实生效与安全上限

让所有任务处理入口共享同一个有效并发门禁，前后端统一限制为 1–2，默认 1。

- **Requirement**: [REQ-20260904-122646](../../tracking/requirements-board.md)
- **Proposal**: [任务并发配置真实生效与安全上限](2026-09-04-effective-task-concurrency-limit.md)
- **Status**: complete

## Problem Statement

当前 `task_queue.max_concurrent` 在配置和前端中存在，但主队列没有读取它；正常批处理固定串行，而逐项重试、批量重新识别和多个批处理入口又可能各自启动线程，导致实际并发既不可预测，也可能远大于界面显示值。对 fnOS 的磁盘、网络和 Provider 请求都存在压力风险。

## Target End State

- 用户只能选择并发 1 或 2，默认 1，界面明确说明 NAS 推荐 1。
- 配置保存时后端拒绝布尔值、非整数、0、负数和大于 2 的值，不能只依赖 HTML 控件。
- 启动时面对历史配置或手工篡改配置，运行时仍将有效并发收敛到 1–2。
- 正常批处理在设置为 2 时可以并行处理两个任务。
- 自动扫描、手动批处理、单文件处理、单任务重试、批量重新识别和人工确认共享同一 Pipeline 级门禁，实际文件任务并发不超过配置。
- 同一时刻只运行一个队列调度循环；重复触发不会叠加多个队列 worker 池。

## Scope and Non-Goals

### In Scope

- Pipeline 级并发门禁与有界队列执行。
- 配置默认值、后端校验、前端输入限制和普通用户文案。
- 重试、单文件和确认入口接入统一门禁。
- 并发上限、重复 `run_all`、非法配置和前端合同测试。

### Non-Goals

- 不开放 3 个及以上任务并发。
- 不为刮削、复制、确认分别设置不同并发数。
- 不引入外部队列、进程池或数据库租约系统。
- 不改变任务状态机、文件安全协议或来源删除策略。
- 不提交、不推送、不生成 fnOS 安装包，除非另行授权。

## Proposed Solution

1. 在 import flow 中建立唯一的并发配置解析函数，默认 1、最大 2；运行时对历史异常值保守钳制。
2. PipelineRunner 持有共享任务槽位协调器。所有实际处理入口通过上下文门禁进入，活跃任务达到上限时等待；暂停不改变已运行任务，只阻止后续领取。
3. `run_all` 使用最多两个 worker 的有界调度，只领取当前可提交的任务，并用单实例运行锁防止重复队列循环叠加。
4. 单任务重试和单文件处理继续快速返回，但后台执行统一经过 Pipeline 槽位。人工确认后台 worker 同样占用槽位。
5. 后端高级配置更新严格验证 `task_queue.max_concurrent`；配置读取兼容缺失值和历史超限值。
6. 前端输入 `min=1 max=2 step=1`，保存前整数钳制到 1–2，并说明默认/推荐值与资源影响。

## Test Plan

- 单元：配置 `None/1/2/3/字符串/布尔值` 的有效值与保存拒绝行为。
- 并发：三个阻塞任务在上限 2 时同时活跃数峰值为 2，第三个等待；上限 1 时峰值为 1。
- 调度：重复调用 `run_all` 时第二个调用不创建额外 worker，不重复领取任务。
- 入口：重试与确认同时执行时仍共享上限；批量重新识别前端不再造成无界后台处理。
- UI：输入最大值 2、步长 1、推荐文案和保存钳制合同。
- 回归：任务状态/CAS、文件流、同剧批量套用、完整 pytest。

## Acceptance Criteria

- 配置为 1 时所有任务入口的实测峰值并发为 1。
- 配置为 2 时主队列实测峰值并发为 2，三个任务均完成且第三个没有提前进入执行体。
- 手工配置为 99 时运行时峰值不超过 2；API 保存 99 返回明确错误。
- 重复点击批量扫描不会形成两个并行调度循环。
- 前端无法通过输入框提交 3 以上值，后端对绕过前端的请求仍拒绝。
- 现有同剧批量重新识别保持功能正确，不自动入库或移动文件。

## Decision Rationale

选择 Pipeline 级共享门禁，是因为多个 API/Watcher 入口最终都使用同一个 Pipeline 实例；在这一层限制可以覆盖线程来源，而单纯修改前端或 `run_all` 无法约束重试和确认。最大值 2 能在低功耗 NAS 上提供有限吞吐提升，同时避免开放用户难以评估的高并发。

## Constraints and Boundaries

- 任务领取继续使用现有 SQLite CAS，防止同一任务被重复处理。
- `run_all` 只能在有空闲 worker 时领取下一任务，避免把等待任务提前标记为 RUNNING。
- 文件移动、替换和来源处置安全边界不变。
- 并发协调仅在进程内；不声称支持多进程共同执行。

## Risk Analysis

- **死锁或槽位泄漏**：上下文管理器使用 `finally` 归还槽位，并测试异常路径。
- **任务提前进入 RUNNING**：有界提交，仅在 worker 名额可用时领取。
- **重复调度**：Pipeline 级非阻塞 `run_all` 锁，重复调用记录并返回。
- **配置热更新**：每次获取槽位读取当前 Pipeline 配置；降低上限不会中断已运行任务，只限制新任务。
- **旧测试桩缺少门禁方法**：服务入口以兼容上下文封装接入，并补轻量 Pipeline 测试。

## Representative Proof Slice

构造三个阻塞任务并设置并发为 2：前两个同时进入处理体，第三个保持等待；释放一个任务后第三个进入，最终峰值严格等于 2。随后用同一 Pipeline 同时触发重试和确认，证明两者不能突破该上限。

## Rejection Criteria

- 配置显示 1，但批量重新识别仍可同时执行多个任务。
- 设置 2 后主队列仍固定串行。
- 输入或 API 可以保存 3 以上并发。
- 为实现并发而提前把大量排队任务标成 RUNNING。
- 重复运行入口形成多个独立 worker 池绕过总上限。
