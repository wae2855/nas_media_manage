# 任务并发配置真实生效与安全上限

- **Requirement**: [REQ-20260904-122646](../../tracking/requirements-board.md)
- **Plan**: [实施计划](2026-09-04-fix-effective-task-concurrency-limit-plan.md)

## 问题（现状与痛点）

界面和配置文件虽然存在最大并发数，但主队列没有消费该值；普通批处理固定串行，逐项重试和多个运行入口又可能绕过它启动多个线程。因此“配置为 1”并不等于实际并发为 1。

## 目标（可验证）

- 前后端统一只允许并发 1–2，默认和推荐值为 1。
- 所有实际任务处理入口共享 Pipeline 级并发门禁。
- 主队列在配置 2 时真实并行两个任务，同时不提前领取大量任务。
- 重复运行入口不叠加 worker 池。

## 方案概述（推荐方案 + 关键取舍）

在 import flow 建立并发配置唯一解析函数和 Pipeline 共享槽位；`run_all` 使用最多两个 worker 的有界调度，其他入口继续使用后台线程，但进入任务处理或确认前必须取得同一槽位。后端保存严格拒绝非法值，运行时对历史或手工修改的超限值钳制到 2。

选择进程内线程门禁而非外部队列，因为 fnOS 当前是单 Python 服务进程，能够以最小变更覆盖现有入口并保留任务 CAS 和文件安全协议。

## 影响面（代码/配置/API/测试/文档）

- 代码：import flow runner/confirm、配置应用服务和前端高级系统设置。
- 配置：`task_queue.max_concurrent` 合法范围固定为 1–2。
- API：高级配置更新对非法值返回 400；现有路由不变。
- 测试：并发峰值、有界领取、重复调度、保存校验、前端限制和既有任务回归。
- 文档：配置、任务、API、前端信息架构和回归矩阵。

## 备选方案（为何不选）

- **只修改 HTML max**：可被 API 或配置文件绕过，且不能修复运行时未消费配置。
- **只在 run_all 建线程池**：重试、单文件和确认仍能绕过上限。
- **开放 1–5**：低功耗 NAS 的磁盘与 Provider 压力不可预测，不符合本次限制过大配置的要求。
