# 目标片库冲突确认与安全替换

把目标片库收敛为“默认只新增”的可信边界：任何同作品或同目标路径冲突都先停在任务列表，只有用户逐项明确选择后才允许跳过、改名保留两份或安全替换。

## Problem Statement

当前 `skip/rename/replace/quality` 去重策略会自动处置冲突，其中 `replace/quality` 在新文件成功发布前就把目标片库中的现有影片移入回收；最终目标路径的同名冲突则直接失败。任务详情没有现有文件对比，也没有独立覆盖授权，批量确认还能绕过逐项判断。这个行为与“目标库只新增、替换必须由用户确认”的产品承诺冲突。

旧配置迁移提示同时使用了偏技术且像首次安装步骤的文案，用户无法分辨它只针对升级、重装保留配置或中途更换片库，不触碰影片文件。

## Target End State

- 无冲突任务只在已验证目标根下新增文件。
- 同作品候选和最终同名路径都进入 `PENDING/AWAIT_REVIEW`，目标片库与来源文件保持不变。
- 任务详情明确展示冲突原因、现有文件与待入库文件，提供“保留片库文件”“两个都保留”“替换片库文件”三个逐项动作。
- 替换必须二次确认；现有文件先进入本地回收且有账本，失败时不得永久删除，并尽可能恢复原文件。
- 冲突任务不能通过普通确认或批量确认绕过专用决策。
- 全新空配置不显示旧配置迁移；只有检测到保留的绝对路径规则时才显示，并明确说明只转换规则、不移动影片。

## Target Outcome

用户看到冲突时首先获得确定感：界面先告诉他“现有影片没有发生任何改动”，再让他比较两份文件并做选择。危险动作在视觉上克制但清晰，不能与普通确认入库混在一起。

## Anti-goals

- 不根据分辨率、大小或旧 `quality` 配置自动替换。
- 不在冲突检测阶段移动任何目标文件。
- 不使用永久删除作为覆盖失败的降级路径。
- 不让一个目标根上的任务自动处置另一个目标根中的同作品文件。
- 不把冲突决策混入批量确认。
- 不重做现有胶卷导航、任务详情整体布局或配置视觉主题。

## Scope and Non-Goals

### In scope

- 去重检测改为只读冲突快照，并限定到本任务实际目标根/目录。
- 任务冲突状态、API 决策参数、并发/陈旧快照校验。
- 三种冲突决策及安全替换顺序。
- 任务详情与列表的冲突提示、对比信息和二次确认。
- 批量确认隔离、默认配置收敛、旧自动策略兼容迁移。
- 旧片库规则迁移文案和显示条件。
- 真实临时目录场景测试、API/UI 回归和安全文档同步。

### Out of scope

- 自动判断“哪一份质量更好”并替用户做决定。
- 跨片库根合并或自动搬迁现有影片。
- 影视内容级哈希去重、长期媒体索引或全库数据库重建。
- 改动源目录三种处理模式的总体产品定义；冲突未决期间来源必须保持不变。

## Proposed Solution

### 1. 单一冲突合同

去重服务只产生可持久化的 `dedup_result` 冲突快照，不做文件移动。快照至少包括：冲突类型、目标根、现有路径、预期目标路径、现有与新文件的大小/分辨率/指纹、检测时间和建议改名。语义同作品与最终同名路径使用不同 `conflict_type`，但统一进入待确认。

### 2. 冲突专用确认

普通 `/tasks/{id}/confirm` 只处理非冲突人工确认；存在未解决冲突时必须拒绝。冲突决策通过同一 API 的受限 `conflict_action` 或独立动作服务进入，允许值只有：

- `keep_existing`：片库文件不变，本任务标记已跳过，冲突动作本身不清理来源。
- `keep_both`：在目标目录内生成不冲突的新文件名，只新增。
- `replace_existing`：要求用户二次确认并携带快照指纹，服务端再次验证后执行安全替换。

### 3. 安全替换协议

替换前重新验证目标路径、目标根边界和现有文件指纹。先将新文件完整准备并校验，再将现有文件移入本地回收且确认账本，最后原子发布新文件；发布失败必须尝试恢复现有文件并把任务置为失败/待恢复，绝不调用永久删除。回收目录不可用或恢复无法保证时应在移动旧文件前失败关闭。

### 4. 用户界面

任务卡直接显示“发现片库已有同一影片，现有文件未改动”。详情采用现有影院金色主题中的双列票根式对比：左侧“片库现有文件”，右侧“本次待入库文件”，移动端折为上下两张卡。普通确认按钮替换为三个明确动作；“替换片库文件”使用危险色边框而非高饱和大红，并在二次确认中写出将被回收的具体文件名和路径。

### 5. 旧配置与迁移提示

旧 `replace/quality/skip/rename` 配置读入后统一采用人工确认安全行为，保存时写入 `confirm`。高级配置只说明“发现冲突后等待确认”，不再允许自动覆盖。迁移提示仅由真实的 `_library_migration_error` 驱动，文案改为“检测到本设备保留的旧版入库规则”，并展示“只转换路径规则，不移动、覆盖或删除影片”。

## Decision Rationale

- 复用现有 `PENDING/AWAIT_REVIEW`，避免为冲突新增第二套任务状态；冲突类型作为结构化业务事实保存在 `dedup_result`。
- 使用指纹快照和确认前重检，防止用户打开弹窗后目标文件被外部程序改动。
- 把检测、决策、执行拆开，才能保证“看到待确认时文件零变化”。
- 对多片库只检查本任务实际目标范围，避免硬盘 A 的任务移走硬盘 B 的影片；跨库同作品以后可作为只读提示扩展，但不得成为自动操作依据。

## Constraints and Boundaries

- 遵守 `docs/standards/safety.md`：影视文件删除/覆盖必须走回收站，禁止永久删除降级。
- 目标根必须存在且通过 `realpath/commonpath`、挂载与写权限校验；挂载消失时失败关闭。
- 原生 HTML/CSS/JS，不增加依赖或第七个 CSS 文件；动态路径与片名必须 `escapeHtml`。
- 冲突弹窗不得点击遮罩意外关闭；桌面与手机都必须可读、可操作。
- 保留当前用户未提交工作，不回滚无关改动。

## Assumptions

| Assumption | Status | Evidence / handling |
|---|---|---|
| `dedup_result` JSON 可承载结构化冲突快照 | Verified | 任务表已持久化并在 repository 中反序列化该字段 |
| 现有 `AWAIT_REVIEW` 能保护中转文件 | Verified | 启动清理明确保留该阶段的活跃中转文件 |
| 回收服务能返回可恢复的账本信息 | Verify in Phase 1 | 实施前检查 manager 返回合同；不足则先补安全 API 和测试 |
| 最终文件名可由任务决策固定传入入库服务 | Unverified | 当前底层会重新套模板，实施时需补显式文件名合同 |
| 多片库任务能解析出唯一实际目标根 | Verified with boundary service | 分类结果已绑定 root ID/相对规则；实施时增加断言测试 |

## Risk Analysis

| Risk | Mitigation |
|---|---|
| 替换过程中断导致片库短暂缺片 | 新文件先完整准备；旧文件回收后使用原子发布；失败自动恢复并留账本 |
| 用户确认前目标文件被外部工具替换 | 服务端对路径和指纹做 CAS 式重检，不一致就回到待确认 |
| 语义匹配误报 | 只提示候选，不自动处置；用户可以保留两份 |
| 旧配置仍触发自动策略 | 配置加载兼容但运行时强制人工确认，保存后归一化为 `confirm` |
| 批量确认绕过冲突 | 服务端过滤并返回排除数量，前端禁选/禁用冲突任务的批量确认 |
| 现有大量脏改动造成误覆盖 | 只用精确补丁修改本计划文件，提交前逐文件审查 diff |

## Acceptance Criteria

1. 冲突任务进入待确认时，目标文件、来源文件及其指纹均未改变。
2. 任务列表和详情明确显示“现有文件未改动”，并展示冲突类型与两份文件信息。
3. 未提供 `conflict_action` 的普通确认不能处理冲突；批量确认不会处理冲突。
4. `keep_existing` 不改目标且不因冲突动作清理来源；`keep_both` 只新增不覆盖。
5. `replace_existing` 只有在快照仍有效、回收可用、用户逐项确认时执行；旧文件进入本地回收并可恢复。
6. 替换任一阶段失败不调用永久删除；能恢复时目标保持原文件，不能自动恢复时任务给出明确恢复指引和账本信息。
7. 多片库场景只允许处置本任务实际目标根内的冲突，不触碰其他根。
8. 全新配置不显示迁移提示；保留旧规则时明确说明只转换配置、不触碰影片。
9. 桌面和手机均能完整阅读冲突对比、执行三种动作，弹窗不会因点击遮罩关闭。
10. 本次新增与受影响测试全部通过，文档与代码合同一致。

## Rejection Criteria

- 页面写着“待确认”，但后台已经移动了目标文件。
- 仍存在根据质量自动替换或批量覆盖入口。
- 回收失败后继续永久删除。
- 冲突详情不展示具体文件，只有抽象的“重复”提示。
- 移动端需要横向滚动才能看到选择按钮或路径把布局撑坏。
