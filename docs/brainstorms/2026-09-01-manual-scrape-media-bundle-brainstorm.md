# 手动刮削、入库进度与随片字幕全流程评审

> 本文只记录评审结论和待确认设计，不实施代码。目标是让普通用户从“找对影片”到“安全入库”始终知道发生了什么，并让视频与字幕作为同一个可恢复文件包处理。

## 问题不是一个搜索框

当前手动刮削把“选择候选影片”和“确认入库”连成了一次操作。用户点中候选后，系统只保存少量名称和年份字段，随即进入确认流程；电影/剧集、语言、Provider ID、完整资料、维度映射、目标片库和最终命名没有形成一个可核对的稳定结果。

与此同时，视频和字幕虽然会一起扫描、复制和移动，但还没有形成统一的文件包语义：

- 复制多个文件时，单个字幕的进度可能把总体百分比重置。
- 字幕与数据库记录存在按位置关联的实现，缺失文件时可能错位。
- 字幕语言和最终路径没有在所有阶段可靠更新，详情信息不一定可信。
- 视频先发布、字幕后发布时，字幕失败可能留下“视频已入库、字幕未完成”的半完成状态。
- 中转清理、重启恢复、来源清理、日志和回收站没有统一以“1 个影片任务 + N 个随片字幕”表达。

所以本轮应把它定义为一条完整用户旅程，而不是分别修搜索、进度条和字幕列表。

## 用户真正需要知道的五件事

1. **我选的是不是正确作品**：电影还是剧集、哪一年、哪个语言资料、Provider 来源是什么。
2. **系统准备怎么整理**：识别后的名称、维度、目标片库、相对子目录、视频名和字幕名。
3. **现在进行到哪里**：正在处理中转、复核规则、写入片库，还是处理来源；正在处理第几个文件。
4. **视频和字幕是否完整**：发现了几个字幕、语言是什么、最终叫什么、是否全部成功。
5. **关闭网页是否安全**：确认后任务由后台继续，刷新或关闭 fnOS 页面不会停止。

## 已核实的当前事实

| 事实 | 结论 |
|---|---|
| 手动搜索请求只提交 query/year | 缺少电影/剧集、资料语言和结果数量 |
| 搜索服务对每个 Provider 只取前 5 条 | 不满足用户希望看到 10～20 条的需求 |
| 候选点击后只预览 title/year 并立即 confirm | 没有“先核对、再入库”的安全停顿 |
| Provider 搜索结果具备 ID/type/raw data | 可以用稳定 ID 再取完整详情，不必靠标题二次猜测 |
| TMDB 客户端支持按调用指定语言 | 可以让语言选择控制本地化标题和简介 |
| 任务确认 API 当前同步执行后续流水线 | 大文件移动会占住请求，页面无法持续展示进度 |
| 后台队列和 watcher 独立于浏览器运行 | 可以改造成确认后排队、后台续跑 |
| 字幕表具备源路径、目标路径、状态、语言、错误字段 | 基础数据结构可复用，但当前写入不完整 |
| 多文件最终发布不可能获得文件系统级整体原子性 | 需要“全部暂存校验 + 视频最后发布 + 可恢复回滚”降低半完成风险 |

## 推荐的用户旅程

```text
待人工确认
  → 打开手动刮削
  → 选择电影/剧集/全部、资料语言，输入名称
  → 查看最多 20 个候选
  → 选择一个候选（只更新资料，不开始入库）
  → 返回任务详情核对资料、维度、目标片库和随片文件
  → 点击“确认并在后台入库”
  → 列表与详情持续显示真实阶段和当前文件
  → 完成后明确显示影片、字幕、来源处理三部分结果
```

### 选择候选后的状态

选择候选不是“处理中”。任务继续停留在 `待确认`，并显示：

- `资料已更新，等待确认入库`；
- 手动选择的 Provider、作品 ID、电影/剧集类型和资料语言；
- 新片名、年份、海报和原始标题；
- 重新映射的维度及其来源；
- 目标片库、相对子目录、视频最终文件名；
- 发现的字幕及预计最终文件名；
- 目标冲突或配置异常。

用户确认前，系统不得移动到片库、处理来源或覆盖任何既有文件。

### 确认后的状态

“确认并在后台入库”应快速返回“已加入后台队列”，关闭详情或关闭网页都不影响后台服务。任务列表滚动到并高亮该任务；详情可以重新打开，并只实时更新进度区和文件状态，不重建整个弹窗。

## 手动搜索设计

### 搜索条件

- 类型：`电影`、`剧集`、`全部`；默认使用文件名识别出的类型。
- 资料语言：建议先提供 `简体中文`、`繁体中文`、`英语`、`日语`、`韩语`；默认使用 Provider 配置语言。
- 说明文案：资料语言影响标题和简介展示，不代表影片原始语言。
- 年份继续可选，用于同名作品缩小范围。
- 默认最多 20 条，服务端设置硬上限，移动端在结果区域内部滚动。

### 候选卡信息

- 海报、中文/本地化标题、原始标题；
- 电影/剧集中文标签、年份、TMDB 评分；
- Provider 来源；
- 简介最多三行，展开后查看完整内容。

### 选择候选的数据契约

前端提交稳定的 `provider_type + provider_id + media_type + language`。后端按 ID 读取完整详情，并重新执行：

1. 资料标准化；
2. 维度映射；
3. 规则分类与目标片库解析；
4. 视频和字幕命名预览；
5. 目标冲突预检。

剧集的季/集号仍以文件名或媒体探测结果为准，不能被 TMDB 搜索结果中的剧名覆盖丢失。

## 列表与详情的信息结构

### 任务列表：一眼看结论

待确认时只展示必要信息：海报、片名、年份、电影/剧集、2～3 个关键维度、目标片库、`资料已更新，等待确认`。完整维度放在详情，避免卡片重新拥挤。

运行时展示：

```text
正在复制到中转 · 电影文件 1/3                 63%
10.9 GB / 17.4 GB
```

非字节阶段只显示阶段，不伪造百分比：`正在复核入库规则`、`正在读取影片资料`。

### 任务详情：先结论，后技术细节

1. **作品资料**：海报、片名、原始名、年份、类型、Provider 来源。
2. **入库预览**：目标片库、最终相对路径、视频最终名、冲突结果。
3. **分类判断**：维度值、来源和命中规则；默认折叠次要维度。
4. **随片文件**：视频和每个字幕的源文件名、语言、计划名/最终名、状态。
5. **进度与事件**：五段流程、当前文件、字节进度、关键日志。

确认前展示编辑和确认按钮；确认后进入只读运行态，不能重复确认。

## 视频与字幕的文件包模型

### 发现与关联

- 以规范化基名和明确边界匹配字幕，不能使用“文件名包含”模糊关联。
- 同目录与约定字幕子目录均需有明确规则；结果稳定排序。
- 扫描后即为每个字幕记录语言、大小、指纹和关联视频。
- 扫描后字幕丢失、变化或新增时，应在执行前重新校验并明确提示，不做位置错配。

### 命名

- 最终名使用配置中的字幕命名模板，而不是代码内固定格式。
- 默认建议：`{video_stem}.{language}{extension}`。
- 同语言多字幕在本次文件包内确定性编号，如 `.zh.2.srt`，并在确认页预览。
- 未识别语言使用可理解标签，如 `und`/`语言未识别`，由用户确认，不静默写成含糊名称。
- 已存在同名字幕视为目标冲突，不允许静默覆盖或临时自动改成随机后缀。

### 推荐的安全发布顺序

采用“文件包暂存 + 全部校验 + 视频最后发布”：

1. 视频和全部字幕进入任务专属中转并完成完整性校验。
2. 在目标片库内使用任务专属临时名暂存所有成员，预检所有最终名称无冲突。
3. 先发布字幕，最后发布视频；视频是文件包提交完成的标志。
4. 视频发布前失败，清理或回滚仅属于本任务、且指纹吻合的临时/已发布字幕。
5. 视频发布后立即记录文件包已提交，再处理来源；重启恢复不得重复写入片库。

任何回滚都只能操作任务自己创建且指纹匹配的文件。既有片库文件仍遵守“只新增、不删除、不覆盖”；用户确认替换走现有本地回收安全流程。

### 为什么不选其他方案

| 方案 | 评价 |
|---|---|
| 字幕失败就整部电影重新复制 | 17 GB 等大文件代价过高，重试容易制造重复 |
| 视频先发布，字幕失败作为普通警告 | 用户会看到不完整作品，来源清理和恢复语义复杂 |
| 文件包暂存、视频最后发布 | 推荐；改动较大，但最符合“完整作品一次出现”和数据安全 |

## 进度与状态文案

任务字节进度按视频加全部字幕的总字节聚合，整个阶段单调递增；同时显示当前成员：

- `正在复制到中转 · 电影文件 1/3`
- `正在复制字幕 2/3：Forrest.Gump.zh.srt`
- `正在校验随片文件 3/3`
- `正在写入「电影」片库 · 全部文件 14.8 GB / 17.4 GB`
- `影片和 2 个字幕已入库，正在处理来源`

建议增加任务进度字段：`progress_item_name`、`progress_item_kind`、`progress_item_index`、`progress_item_total`。现有字节字段表达整个文件包，不再被单个字幕回调重置。

最终结果分开表达：

- 绿色：`影片和 2 个字幕均已入库，来源处理完成`；
- 黄色：`影片和字幕已入库，来源目录未完成处理`；
- 黄色：`影片已入库，1 个字幕需要处理`（只用于无法回滚的极少恢复场景）；
- 红色：`入库未完成，片库未出现新影片`。

不能把来源处理失败或字幕残缺隐藏在普通“成功”中。

## 中转、日志、回收与重启恢复

### 中转

- 中转记录以任务文件包为单位，包含视频、字幕、每个成员指纹及状态。
- 文件包提交成功后才清理中转；失败内容保留并给出原因和可恢复动作。
- 启动恢复必须直接读取字幕记录，不能依赖不包含字幕附件的任务列表快照。

### 日志

日志记录阶段边界，不按每个数据块刷屏：发现字幕数量、单个成员开始/完成、命名结果、完整性校验、提交、回滚和来源处理。

每条关键事件带 `task_id`、成员类型和文件名，详情页显示普通人文案，技术日志保留诊断字段。

### 回收站

- 整组来源处理以 `影片文件夹（1 个视频 + N 个字幕 + M 个其他文件）` 展示。
- 单任务回收按 task/bundle 分组，默认展示成员数量，展开才看单文件。
- 恢复默认恢复整组；若允许单文件恢复，必须明确提示作品可能不完整。
- 目标片库冲突替换产生的旧文件仍进入本地回收，不能与来源清理混为一组。

### 重启恢复

- 确认入库后，浏览器关闭不影响后台任务。
- 服务重启时依据文件包状态和指纹恢复：未提交则继续/回滚暂存；视频提交标记存在则只补齐状态和来源处理，绝不重复入库。
- 来源挂载失效时保留片库结果并显示黄色警告，不直接删除或误判来源已清理。

## 关键假设审计

| 假设 | 状态 | 结论 |
|---|---|---|
| Provider 可用稳定 ID 获取详情 | 已验证 | 可实现可靠的候选应用 |
| TMDB 可按请求指定资料语言 | 已验证 | 语言选择可落地 |
| 字幕表可保存逐成员状态 | 已验证 | 需要补齐写入与恢复，不必重建模型 |
| 后台队列可独立浏览器继续运行 | 已验证基础能力 | 需增加“已确认任务续跑”入口和幂等锁 |
| 多文件能一次原子发布 | 不成立 | 必须用暂存、视频最后发布和受限回滚近似保证 |
| 当前字幕匹配和命名已可靠 | 不成立 | 必须纳入本轮修正 |

## 自评审结论

推荐方案满足“省心”的前提：用户只需要做两次明确判断——选对作品、确认入库；其余过程由后台执行，但每个长耗时和异常都有可理解的状态。

本方案改动不是小修，涉及手动处理 API、任务续跑状态、字幕数据一致性、文件包提交/恢复、任务 UI 和回收展示。必须分阶段实施，以“先证明完整文件包安全，再接 UI”作为交付门槛；在文件包失败恢复、片库保护和浏览器关闭续跑未通过前，不应生成 fnOS 验收包。

## 待产品确认

- 采用“选择候选只更新资料，另点确认才后台入库”。
- 手动搜索默认最多 20 条。
- 采用“文件包暂存、字幕先发布、视频最后发布”的安全策略。
- 同语言多字幕在本次文件包内使用确定性编号，既有目标冲突继续阻断并让用户决定。
