# 任务异常退出与最少大文件传输全流程评审

## 用户真正想完成的事情

普通用户不关心状态机名称，只关心三个问题：

1. 这部新资源还要不要继续整理？
2. 已有片库文件是否绝对不会被误删？
3. 不要的新资源是保留、进入本地回收区，还是在已开启高风险模式时永久删除？

任务记录和来源文件不是同一件事。删除记录不能暗中删除文件；处理来源失败也不能先把任务记录删掉。所有动作必须先留下可理解的结果，再允许用户单独移除历史记录。

## 已核实的现状

- 列表按钮写“移入回收”，请求却发送 `delete_files=false`，后端只删除任务记录，文案与事实相反。
- 运行中任务被服务端直接拒绝删除；取消只支持 `PENDING/QUEUED`，不能请求安全停止正在刮削、复制或入库的任务。
- 待确认、失败、跳过和取消状态的按钮分布不一致；已完成任务没有明确的“只删记录”动作。
- 目标冲突中的“保留片库文件”会结束为 `SKIPPED` 并保留来源，但用户不能同时选择回收这次新资源。
- 当前大文件顺序已经是先刮削、分类、命名、判重，确认后才复制；这条正确边界必须保持。
- 确认后仍固定执行“来源→中转→目标片库”。目标侧本身已有任务专属暂存、完整性校验、no-replace 发布和文件包恢复能力，因此新任务可直接从来源写入目标暂存，省去一次完整中转复制。

## 全状态业务矩阵

| 当前状态 | 用户可理解动作 | 来源处理 | 目标片库 | 结果 |
|---|---|---|---|---|
| 排队中 | 放弃这次整理 | 保留 / 本地回收 / 已授权的永久删除 | 不接触 | 已取消 |
| 处理中，尚未提交片库 | 停止并放弃 | 先请求安全停止，再按选择处理来源 | 不新增、不删除 | 停止中 → 已取消 |
| 处理中，目标文件包已提交 | 不再允许停止 | 等待来源收尾和记录完成 | 保留已提交结果 | 正常完成或来源警告 |
| 待确认（普通） | 放弃这次整理 | 保留 / 本地回收 / 已授权的永久删除 | 不接触 | 已跳过 |
| 待确认（重复） | 保留片库现有文件 | 新资源保留 / 本地回收 / 已授权的永久删除 | 原文件不变 | 已跳过，并写清来源结果 |
| 失败 | 不再处理 | 保留 / 本地回收 / 已授权的永久删除 | 不接触；若已提交则只删记录 | 已跳过或保留失败事实 |
| 已跳过 / 已取消 | 处理遗留来源 | 保留 / 本地回收 / 已授权的永久删除 | 不接触 | 更新来源结果 |
| 已完成 | 删除任务记录 | 默认只删记录；若来源仍存在，必须单独明确选择 | 永远不删除 | 记录移除，片库不变 |
| 重新整理任务 | 放弃重新整理 | 只结束新任务 | 原片库文件保持原位 | 已取消/已跳过 |

混合批量选择不做“猜测式统一动作”。界面先统计可执行、需停止、只可删记录和受保护数量；提交后逐项返回结果。片库文件始终不进入来源处置集合。

## 三种方案

### A. 一个“删除”按钮自动猜行为

实现最小，但用户无法预知会删记录、回收来源还是删除文件；当前问题正来源于此，否决。

### B. “结束处理”与“删除记录”分离（采用）

- 活动或异常任务使用“结束处理”；弹窗选择来源去向。
- 已完成或已形成终态的任务使用“删除记录”；明确声明片库文件不受影响。
- 目标重复在冲突卡片内直接提供“保留片库并保留新资源 / 回收新资源”，不让用户跨页面猜下一步。
- 运行中采用协作式停止：只在安全检查点生效；文件包提交后拒绝停止。

认知成本最低，并能保持审计与文件安全边界。

### C. 强制终止线程并递归删除

可能留下半个复制文件、破坏文件包发布或误删同来源目录其他任务，否决。

## 最少传输方案

冻结顺序：

```text
只读发现 → 刮削 → 维度/规则 → 最终路径和命名 → 片库冲突 → 人工决策
  → 才允许大文件传输
```

新任务默认采用“来源→目标任务暂存→校验→字幕先发布→视频最后发布”。来源在目标提交前保持原样：

- 保留来源：目标提交后来源不动，一次大文件复制。
- 本地回收来源：目标提交后再移动来源；同盘是重命名，跨盘回收才产生用户明确选择的第二次复制。
- 永久删除来源：目标提交并校验后走既有隔离区/账本删除，不产生回收副本。
- 已有有效中转断点：继续使用旧中转，不重新读取来源。

中转不再是每个新任务的必经站。它保留为旧任务断点、恢复兼容和未来明确需要本地快照的策略能力。目标暂存文件只属于当前任务，可续传、可校验，不能覆盖现有片库文件。

## 停止语义

运行中点击“停止”不是杀线程：

1. 数据库记录 `停止请求` 和用户选择的来源去向。
2. 刮削/规则步骤在下一步前检查；大文件传输每个进度块检查。
3. 视频发布前收到请求，文件包按任务清单回退，片库不留下半成品。
4. 视频已提交后收到请求，拒绝取消并继续收尾，避免把已入库作品谎报成取消。
5. 停止成功后清理任务专属临时文件，再处理来源；来源处理失败则保留任务和错误，不删除证据。

## 假设与风险审计

- 假设目标侧任务暂存支持当前文件系统；不支持或权限变化时失败关闭，不回退为覆盖。
- 远程源挂载可能在传输中断开；目标 `.copying` 保留为断点，来源恢复后可重试。
- 一个来源文件夹可能包含多个有效视频任务；单任务放弃只处理该任务登记的视频和字幕，不递归清空整个来源单元。整组清空仍只由“全部任务成功”的来源单元协调器执行。
- 永久删除只在全局高风险来源处置已明确启用时出现；否则任务页只提供保留和本地回收。
- 已提交到片库的文件永远不属于普通任务删除范围。

## 验收视角

- 用户能在卡片和详情一眼看懂“继续、停止、保留片库、处理新资源、删除记录”的区别。
- 每种状态都能走到明确终态，没有“已完成又需确认”。
- 运行中停止在真实前端可看到“正在安全停止”，最终来源去向与文件系统一致。
- 重复片选择保留片库时，片库指纹不变，新资源按选择保留或回收。
- 新任务在确认前不创建中转或目标大文件；确认后默认只发生一次来源到目标的有效载荷复制。
