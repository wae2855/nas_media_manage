# fnOS 首次启动目录授权与多片库头脑风暴

## 已确认的问题

1. fnOS 安装 `python312` 时长约五分钟，但依赖包安装过程缺少细粒度反馈，容易被误判为卡死。
2. 用户的影片可能分布在四五块硬盘，单一 `library_root` 无法表达真实片库拓扑。
3. fnOS 原生安装向导没有目录选择字段，要求用户手填路径既容易错，也没有完成共享目录授权。

## 事实边界

- 应用无法控制 fnOS 依赖包 `python312` 的安装进度 UI；应继续声明官方运行时依赖，不私自内嵌另一套 Python。
- fnOS 1.2.0401 的开放能力提供共享目录授权/选择；选择动作属于首次 Web 启动体验，而不是原生安装向导字段。
- 来源和目标可位于本地或已挂载远程目录；回收、中转、数据库和日志仍只允许本地目录。
- 多片库不能退回“规则写任意绝对路径”，每条规则必须绑定稳定的片库根 ID，并继续执行保存时与运行时双重越界校验。

## 方案比较

### 安装依赖

- 内嵌完整 Python：包体大、补丁和架构维护困难，且偏离 fnOS 官方依赖模型，不采用。
- 在线 pip：包小但存在网络失败和第二段无反馈等待，不采用为默认路径。
- 保留 `python312` 依赖并离线携带项目 wheel：仍有一次系统 Python 安装，但应用依赖不再联网，采用。

### 多片库数据模型

- 多个绝对目标：简单但无法形成授权和安全边界，不采用。
- 每条规则直接保存根路径：改名/迁移重复且容易漂移，不采用。
- `library_roots[]` + 稳定 ID + 规则绑定 ID：可检查、可迁移、可展示，采用。

### 目录选择

- 安装向导手填：没有浏览/授权能力，不采用为主路径。
- 首次 Web 启动调用 fnOS 目录授权选择器：采用。
- 普通浏览器或接口不可用时手工输入：作为明确降级，保存前仍强校验。

## 拍板方案

1. 旧单根配置无损迁移为 `library_roots[default]`，所有旧规则和兜底目录绑定 `default`。
2. 每个片库根包含 `id/name/path/enabled`；ID 唯一且保存后稳定。每条规则包含 `library_root_id`；兜底目录也显式绑定根。
3. 首次启动按“来源 → 一个或多个片库 → 本地回收 → 最终检查”引导。片库通过“继续添加”支持多个目录。
4. fnOS 选择器不可用时显示原因和手动输入，不伪装成已授权；所有目录都必须通过存在、权限、存储身份和容量检查后才能开始。
5. 安装包按目标架构携带离线 wheel；安装日志写入阶段进度，失败时给出可诊断原因。fnOS 安装 `python312` 本身仍由系统展示和管理。

## 风险与缓解

- 根被删除但规则仍引用：禁止删除被使用的根，或要求先迁移规则。
- 同一路径重复添加：规范化真实路径后去重。
- 远程片库掉线：保留配置，标记离线并阻止相关自动任务，不自动创建同名目录。
- fnOS API/客户端版本不足：回退手动输入并给出版本提示。
- 离线 wheel 架构不匹配：按 x86/arm 分包构建，构建时校验 wheel 平台。

## 验收要点

- 旧配置升级后分类结果不改变。
- 可添加至少五个片库根，每条规则可清楚选择目标片库。
- 规则无法写到其绑定根之外；所有根都出现在存储检查中。
- fnOS 内可点选并授权目录；非 fnOS 环境仍可手填。
- 应用依赖安装不访问公网，失败日志能区分系统 Python 与项目依赖阶段。
