# 配置依赖、来源单元与开场检查

## Problem Statement

当前配置流程虽然已经减少首次参数量，但仍按技术模块平铺：源视频处理与垃圾清理并列、规则可指向未经存储检查的任意绝对路径、LLM 开关与配置入口分离、高级配置脱离胶卷上下文、完成页把存储 READY 与业务模拟混为一谈。用户无法从卡片层级理解“选择什么会启用什么”，系统也不能用一个可信结论回答“现在是否可以开始”。

## Context

- 现有页面保留了 cinema 黑金主题和胶卷阶段导航，这是正向参考，不能改变。
- `source_policy.cleanup_source_after_done` 与 `source_cleaner.enabled` 当前是两个独立布尔值；UI 允许“保留源视频但清理垃圾”，也允许缺少明确父级的组合。
- 当前源清理服务以单视频和伴生字幕为单位，不能证明一个顶层来源文件夹内的全部任务都已完成。
- `path_rules[].template` 与 `fallback_dir` 当前保存绝对路径，存储检查只能反推公共根，保存时没有强制包含关系。
- 当前完成页 READY 主要来自存储检查；模拟器只验证文件名、Provider、刮削、维度和分类落点。

## Chosen Approach

### 三种来源处理模式

1. `preserve_all`：保持源目录不变；不运行垃圾清理；源只需读权限。
2. `preserve_media`：保留影视与受保护关联文件，按清理策略回收垃圾；允许高级规则和可选 LLM。
3. `recycle_source_unit`：当同一来源单元内全部媒体任务成功后，将整个来源单元移入本地回收站；任一任务失败、待确认、处理中或文件仍变化时整体保留。

来源根目录本身永远不移动。每个顶层文件夹是独立来源单元；直接位于来源根的全部文件共同形成一个“根散文件单元”，避免无同名关系的说明和广告文件残留。来源单元生成版本快照，清理前复核内容、任务状态、挂载身份和回收容量。

### 片库根目录

存储检查持有一个明确、已存在、已校验的 `library_root`。片库整理只编辑相对模板，后端用 `realpath/commonpath` 验证最终路径仍在根内。旧绝对规则位于同一公共根时迁移为相对模板；跨根规则进入 BLOCKED，不自动猜测。

### 上下文依赖配置

LLM 只属于 `preserve_media` 的垃圾判断策略。用户启用时在选项内部打开复用的配置弹层，完成配置与连接测试后回到原位置。`recycle_source_unit` 在产品文案中称为“入库后清空来源”；最终仍整体进入安全回收链路，但主流程不展示单元边界、稳定窗口和容量门禁等实现参数。

### 高级配置整合

高级项不再跳出胶卷壳形成平行首页。“进阶设置”成为胶卷轨道中的普通一站，命名、维度、安全和系统设置在同一站原位展开；文件来源管理清理/LLM，自动运行直接管理 watcher 开关和轮询周期。

### 开场检查

完成页主动作改为“执行开场检查”。检查配置契约、存储、权限、挂载、容量、TMDB、条件性 LLM、网络与自动运行门禁；输出 `PASS/WARN/BLOCKED/SKIPPED`。只有 BLOCKED 为零才显示“可以开始”。影片模拟保留为独立的业务效果验证。

## Why This Approach

它把用户选择、系统权限和运行门禁绑定在同一事实模型中：页面层级不再只是视觉包含关系，后端也拒绝不可能或越界的组合。相比新增更多提示文字，显式枚举和根目录契约更可测试，也能阻止旧客户端绕过前端。

## Subjective Contract

- Target outcome：用户一眼看懂“我选择的处理方式会展开哪些子策略”，完成页能明确回答能否开始。
- Anti-goals：不做白底设置后台；不增加第二套全局导航；不把所有高级参数塞回首次流程；不把模拟成功等同系统就绪。
- References：现有胶卷阶段导航、黑金影院 tokens、存储检查角色卡。
- Anti-references：当前独立高级配置首页、并列且无父级的源清理卡、规则中的任意绝对路径。
- Tone：结论优先、风险直说、默认项可忽略、阻塞项给出修复入口。
- Rejection criteria：胶卷导航消失；模式 1 仍可启用清理；越界规则可保存；LLM 启用后无配置入口；完成页未真实检查却显示 READY。

## Preview And Proof Slice

- Proof slice：文件来源三模式父子卡片、LLM 上下文弹层、完成页开场检查清单。
- Required previews：1440×1024 与 390×844；三个模式逐一切换；高级设置展开/返回；开场检查 PASS/WARN/BLOCKED。
- Rollout rule：证明切片无横向溢出、console error 为 0、状态来自后端后，再迁移片库整理和其他高级项。

## Key Design Decisions

### Q1: 模式 3 的清理单位 — RESOLVED

**Decision:** 顶层来源文件夹整体等待、整体回收；任一媒体任务未成功则不清理。来源根的全部直接文件形成一个根散文件单元，全部直接媒体成功后整体清空这些文件并保留根目录。

**Rejected:** 成功一个视频就删除一个视频。它会把多集/多影片下载包拆散，并可能破坏下载器或用户恢复预期。

### Q2: 片库规则路径 — RESOLVED

**Decision:** 单一已校验片库根加相对模板。

**Rejected:** 继续保存任意绝对路径并只做权限测试，因为不能证明其属于用户已确认的目标。

### Q3: 最终检查与模拟 — RESOLVED

**Decision:** 开场检查回答运行就绪，模拟回答刮削和分类效果；两个动作独立展示。

**Rejected:** 扩展现有模拟器承担全部检查，因为目录和网络诊断会污染影片处理时间线。

## Assumption Audit

| Assumption | Status | Evidence / Handling |
|---|---|---|
| 顶层文件夹可作为默认来源单元 | Verified with boundary | 用户明确以“阿甘正传”文件夹为整体；根散文件形成单一保守单元 |
| 一个来源单元可能含多个媒体任务 | Verified | 现有 scanner 按媒体文件建任务，必须增加单元关联与聚合状态 |
| 所有旧规则能自动迁移到单根 | Unverified | 仅同一公共根自动迁移；否则 BLOCKED 并要求用户选择 |
| LLM 未启用不应阻止开始 | Verified | ADR-0010 规定 LLM 只服务可选源目录清理 |
| 外部网络探测可代表 TMDB 可用 | Weak | 不做泛化联网测试；直接调用实际 Provider/LLM 测试端点 |

## Open Questions

- 多片库根目录留作后续高级能力，本轮只支持一个 `library_root`。
- 真实 fnOS 升级中旧绝对规则的迁移仍需设备验收。

## Out of Scope

- 不改变维度值映射和限制级归一。
- 不实现网盘协议客户端。
- 不永久删除回收站内容。
