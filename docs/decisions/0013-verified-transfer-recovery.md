# ADR-0013: 可验证传输、回收与中断恢复

Date: 2026-08-28
Status: Accepted
Requirement: REQ-20260828-151346

## Context

当前跨设备移动在 rename 失败后采用 `copy2 → remove`。该流程没有目标临时名、传输日志、复制前后源快照、目标完整性证明和崩溃恢复；回收元数据可能在删除源后写入且失败被忽略。云盘断线、进程退出或空间耗尽时可能留下半成品，甚至删除无法证明已完整复制的源。

Python 官方文档明确：`shutil.move` 跨文件系统会回退为复制后删除，`copy2` 也不提供事务语义；同文件系统的 `os.replace` 成功时才具备原子替换性质。因此跨设备可靠性必须由应用层协议提供。

## Decision

1. 所有跨设备文件移动统一走持久化 transfer operation，不允许业务代码自行 `copy2 + remove`。
2. 统一链路为“来源 → 本地中转 → 目标同目录临时文件 → 正式目标”。远程 A 到远程 B 也禁止直传，必须经本地中转，便于断点、校验和容量预留。
3. 协议为：记录操作和源快照 → 复制到本地中转并计算 SHA-256 → 写目标临时文件 → flush/fsync → 校验大小与源版本 → 按风险回读目标摘要 → 原子发布 → fsync 父目录（平台支持时）→ 提交目标状态 → 最后处理源 → 提交完成。
4. 源在复制期间发生 size/mtime 变化时，目标临时文件不发布，操作进入 `WAITING_SOURCE_STABLE`。
5. 重启后从操作日志和临时文件恢复；只有源版本、目标临时文件和已记录偏移一致时续传，否则安全重启复制。
6. 目标已发布但源未处理时，重试只能完成源处理，不得重复发布目标。
7. 回收记录使用服务端 SQLite ID 和 canonical path；API 不接受客户端任意路径。回收、恢复、覆盖恢复都复用同一传输协议。
8. 覆盖恢复时，原位置现有文件先进入本地回收形成新记录，禁止直接永久删除。
9. 入库结果和源清理结果分开持久化。入库成功、清理失败显示为“入库成功，清理待处理”，并允许只重试清理。
10. 清理预览生成带文件版本的计划；执行逐项复核，只操作用户确认且未变化的对象，并与活跃任务路径租约互斥。
11. 任务由数据库 CAS 原子领取，单一调度入口保证同一任务和源路径只有一个有效执行租约。

### 完整性最低证明

| 场景 | 发布前证明 | 允许处理源的条件 |
|---|---|---|
| 本地中转同卷 rename 到本地目标 | 中转 SHA-256 + size；rename 后身份一致 | 发布和父目录同步完成 |
| 本地中转复制到另一块本地盘 | 源 SHA-256 与目标回读 SHA-256 相等 | 目标发布和记录提交完成 |
| 任意远程目标 | 源 SHA-256 与远程目标回读 SHA-256 相等 | 目标仍在线、身份未变、记录提交完成 |
| 来源移入本地回收 | 来源 SHA-256 与回收副本回读 SHA-256 相等 | 回收记录已提交后才删除来源 |
| 来源明确保留 | 中转/目标按上述规则验证 | 不处理来源 |

远程回读失败、摘要不一致或父目录同步无法确认时，操作保持可恢复状态，禁止删除或清理来源。

## Consequences

- 本地同文件系统 rename 仍保留快速路径；跨设备多一次记录和校验成本。
- SHA-256 在复制来源到本地中转时流式计算；远程目标和任何随后处理源的链路必须回读目标并比较摘要，因此会增加网络读流量。
- transfer/recycle ledger 必须保存在本地 SQLite，不能放在远程挂载。
- 旧 sidecar 元数据只作为迁移兼容输入，不再是唯一事实源。

## Alternatives

- 继续依赖 `shutil.move`：无法提供中断恢复和删除前完整性证明，否决。
- 所有文件强制完整哈希两遍：最安全但对大型影片和低性能 NAS 成本过高，作为高风险链路策略而非全局固定要求。
- 只使用 sidecar：无法可靠支持查询、幂等状态和崩溃恢复，否决。
