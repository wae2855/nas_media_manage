# 开发流程规范

> 本文档定义 影音库AI智能整理的开发流程标准，所有开发活动必须遵循此规范。

---

## 1. 总体流程

完整开发流程分为五个阶段，每个阶段有明确的输入、输出和质量门：

| 阶段 | 输入 | 输出 | 质量门 |
|------|------|------|--------|
| 方案设计 | 需求描述 | 方案文档（📋 待评审） | 包含目标、现状分析、改动清单、数据流变化、风险与缓解 |
| 开发计划 | 已评审方案 | 计划文档 | 阶段按依赖排列、每阶段有验收标准、标注涉及模块 |
| 代码实现 | 计划文档 | 可运行代码 | 遵循编码规范、增量提交、无 lint 错误 |
| 测试验证 | 可运行代码 | 通过的测试 | 单元→集成→前端三层测试全部通过 |
| 文档回写 | 变更清单 + 通过的测试 | 更新后的文档 | 方案/架构/规范/总览文档同步更新，方案标记 ✅ 已实施 |

**阶段流转规则**：前一阶段质量门未通过，不得进入下一阶段。例外情况需在计划文档中说明。

---

## 2. 方案设计阶段

### 2.1 方案文档规范

- 方案文档存放在 `docs/方案/` 目录
- 文件命名：`<功能描述>.md`，如 `回收站与安全操作改造.md`
- 方案文档必须包含以下章节：

| 章节 | 内容 |
|------|------|
| 目标 | 本次改造要达成什么，用表格列出需求与核心原则 |
| 现状分析 | 当前系统如何工作，涉及哪些代码位置（标注文件名和行号） |
| 改动清单 | 逐项列出需要修改的模块、文件、函数 |
| 数据流变化 | 改造前后数据流对比，用流程图或表格说明 |
| 风险与缓解 | 可能的副作用及应对策略 |

### 2.2 方案状态管理

方案文档标记状态，状态流转如下：

```
📋 待评审 → 🔄 进行中 → ✅ 已实施
```

- **📋 待评审**：方案初稿完成，等待评审
- **🔄 进行中**：方案评审通过，开始实施
- **✅ 已实施**：实施完成且文档已回写

### 2.3 方案是活文档

实施过程中如有偏差，必须回写更新方案文档。偏差包括但不限于：

- 字段名调整
- 流程变更
- 接口变化
- 新增或删除功能点

后续变更如果影响已有方案，应在原方案基础上更新，而不是创建新方案。只有全新模块才创建新方案文档。

### 2.4 强制要求

- 新功能必须先写方案，评审后再实施
- Bug 修复需先定位根因，确认影响范围再改
- 重构需先确认测试覆盖，增量迁移

---

## 3. 开发计划阶段

### 3.1 计划文档规范

- 计划文档存放在 `docs/计划/` 目录或 `.trae/documents/`
- 计划文档是一次性文档，实施完成后不再维护

### 3.2 计划必须包含

| 项目 | 说明 |
|------|------|
| 阶段划分 | 按依赖顺序排列，前置阶段必须先完成 |
| 验收标准 | 每个阶段定义明确的完成条件 |
| 影响范围 | 标注涉及的模块和文件 |
| 依赖关系 | 阶段间的依赖和并行可能性 |

### 3.3 计划执行

- 按计划顺序实施，增量提交
- 每完成一个阶段，验证验收标准
- 如发现计划不合理，调整计划并记录原因

---

## 4. 代码实现阶段

### 4.1 编码规范

| 规则 | 说明 |
|------|------|
| 跨子包导入 | 用完整路径：`from media_importer.core.db import ...` |
| 同子包内导入 | 用相对导入：`from .utils import ...` |
| 注释 | 不加注释，代码自解释 |
| CSS 颜色 | 使用变量体系 `var(--text-primary)`，不硬编码颜色值 |
| 前端 JS | 按功能拆分：api/config/tasks/path-rules/prompts/dimensions/app |

### 4.2 配置变更规范

配置键变更必须在 `core/config_loader.py` 添加自动迁移逻辑，确保向后兼容。

新增配置项需全链路同步更新：

```
config_loader → config_validator → config_handlers → 前端
```

### 4.3 状态变更规范

新增任务状态需全链路更新：

```
constants.py → task_manager.py → pipeline/ → api/ → 前端
```

状态流转必须符合状态机规则，不允许非法跳转。`file_location` 追踪文件当前位置，与状态保持一致。

### 4.4 安全规范

- 敏感信息（api_key/secret）返回前端时脱敏为 `***`
- 文件路径必须校验，防止路径穿越
- 不提交密钥和凭据到代码仓库

### 4.5 提交规范

- 按计划增量提交，每次提交对应一个逻辑完整的改动
- 提交信息清晰描述改动内容

---

## 5. 测试验证阶段

### 5.1 测试层次

| 层次 | 范围 | 工具 | 文件命名 | 目录 |
|------|------|------|---------|------|
| 单元测试 | 单函数/类 | unittest | `test_<模块>.py` | `tests/` |
| 集成测试 | API 端到端 | unittest + urllib | `test_integration_<功能>.py` | `tests/` |
| 前端测试 | UI 交互 | Playwright | `test_frontend_<功能>.py` | `tests/` |

### 5.2 测试要求

- 后端单元测试覆盖核心逻辑路径
- API 变更必须有集成测试验证
- 前端 UI 变更必须有 Playwright 测试
- 所有测试必须通过后才能标记阶段完成

### 5.3 测试执行顺序

1. 先运行单元测试，确保基础逻辑正确
2. 再运行集成测试，验证 API 端到端流程
3. 最后运行前端测试，验证 UI 交互

### 5.4 测试与开发的关系

- 重构前必须确认测试覆盖，增量迁移
- Bug 修复应补充对应的回归测试
- 新功能必须配套测试用例

---

## 6. 文档回写阶段

大批量代码变更完成后，必须回写更新对应的文档。

### 6.1 回写范围

| 文档类型 | 目录 | 回写内容 |
|---------|------|---------|
| 方案文档 | `docs/方案/` | 实际实现与方案的差异（字段名调整、流程变更、接口变化等） |
| 架构文档 | `docs/架构/` | 模块职责、接口、数据结构等变更 |
| 规范文档 | `docs/规范/` | 新增或变更的规范规则 |
| 总览文档 | `docs/系统架构总览.md` | 数据流、业务流、模块关系等变更 |

### 6.2 回写检查清单

- [ ] 对照变更清单，逐项检查方案文档，更新实际实现与方案的差异
- [ ] 更新架构文档中的数据模型、接口、流程图
- [ ] 补充规范文档中的新增规则
- [ ] 更新系统架构总览中的数据流和业务流
- [ ] 将方案文档状态更新为 ✅ 已实施

### 6.3 回写时机

- 小范围改动：随代码提交一起回写
- 大批量改动：变更全部完成后集中回写，但偏差应在实施过程中实时记录

## 7. 文档体系分层

```
框架层    docs/系统架构总览.md          — 全局视角，模块关系，数据流
模块层    docs/架构/*.md               — 各模块技术文档，职责边界
规范层    docs/规范/*.md               — 开发规范、接口规范、安全规范
方案层    docs/方案/*.md               — 设计方案（活文档，随实现更新）
计划层    docs/计划/ 或 .trae/documents/ — 实施计划（一次性）
```

### 7.1 文档边界原则

- 每个文档有明确的职责边界，不重复描述其他文档的内容
- 文档间通过链接引用，不复制内容
- 架构文档聚焦"是什么"和"怎么做"，方案文档聚焦"为什么这样改"
- 规范文档聚焦"必须遵守的规则"，不包含实现细节

### 7.2 方案文档生命周期

```
新建 → 评审 → 实施 → 回写 → 维护
 📋     🔄    🔄     ✅     ✅
```

1. **新建**：新功能/改造需求 → 创建方案文档（📋 待评审）
2. **评审**：方案评审通过 → 标记（🔄 进行中）
3. **实施**：按方案开发，偏差实时记录
4. **回写**：实施完成 → 回写差异 → 标记（✅ 已实施）
5. **维护**：后续变更涉及已实施方案 → 更新对应方案文档

**重要**：方案文档不是一次性快照，而是活文档。后续变更如果影响已有方案，应在原方案基础上更新，而不是创建新方案。只有全新模块才创建新方案文档。

### 7.3 头脑风暴文档处理

头脑风暴/探索性文档用于前期分析，不作为正式文档归档。分析结论应融入对应的方案文档中，而不是独立保留。

---

## 8. 任务路由

| 任务类型 | 流程 |
|---------|------|
| 新功能开发 | 先写方案到 `docs/方案/`，评审后再实施 |
| Bug 修复 | 先定位根因，确认影响范围再改 |
| 重构 | 先确认测试覆盖，增量迁移 |
| 文档更新 | 与代码同步，不要过时 |
